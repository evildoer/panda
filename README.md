# PANDAMIA Bot 🐼

> 💬 **Говорить по-русски!** — говорят, помогает.
>
> **Это правило проекта, а не только про бота:** в комментариях к коду, строках лога, ответах в чате, README и коммитах пишем **по-русски**, когда язык это позволяет. Английскими остаются только те вещи, где иначе нельзя или не принято: имена команд и опций Discord, названия полей в API (`content`, `roles`), ключи конфига и сами идентификаторы в коде.

Discord-бот для сервера PANDAMIA: модерация голосовых каналов (права владельцев, мут/глухота, тег 🔑), бан-таймаут за выход с сервера, музыка через `/play` (YouTube и др.) и мост между серверами (pipe).

**Стек:** Node.js 24 (портативный, в папке) + discord.js v14 + keyv/sqlite + @discordjs/voice + yt-dlp.

## Запуск

Один файл на всё — **`node.cmd`** в папке бота. Двойной клик по нему (или по ярлыку на него) — бот запускается, окно = живой лог. Из консоли — то же самое:

- `node .` — привычный запуск: в папке бота команда `node` берётся из `node.cmd` (совместимая версия из папки), поэтому работает и без ярлыка;
- `node.cmd` без аргументов — тот же запуск (окно остаётся живым после остановки);
- `node script.js аргументы` — обычный запуск любого скрипта на той же версии Node;
- Node ищется сам: портативный `node-v*-win-x64` в папке бота → системный из PATH;
- **Ctrl+C → Y** — бот остановлен, окно и консоль остаются (можно `git push` и другие дела);
- `node .` в той же консоли — запустить снова; `exit` (или крестик) — закрыть окно;
- **музыка переживает перезапуск (и обновление кода):** очередь, текущий трек, место в треке и канал лежат в базе (`musicState` в `*.sqlite` рядом с ботом), поэтому после `Ctrl+C → node .` бот возвращается в тот же голосовой канал и продолжает **с того же места** (не вышло — берёт тот же трек с начала). Команды заново давать не надо. Очередь не «устаревает» и по времени, и по пустому каналу: она просто ждёт — в канале никого, значит пауза (`😴 нет слушателей`), после падения бот сам зайдёт в тот же канал и включит музыку, как только появится человек, а после `/leave` — по `/join`. **Присутствие хранится отдельно от очереди (v2.24):** если бот просто сидел в канале (`/join`, `/stop`, доигравшая очередь) — после перезапуска он вернётся туда и без единого трека, а не останется «свободен». Стирает очередь только `/stop` (и естественный конец очереди). Подробности и что теряется при аварийном закрытии окна — в разделе «Обновление кода и перезапуск».

Системный node должен быть ≥ 18 (для музыки ≥ 22): если старый — `node.cmd` сам возьмёт портативный из папки, а вне папки бота продолжит работать системный `node`.

**Почему в папке бота версия Node фиксирована (не убирать `node.cmd`).** В `node_modules` лежат native-модули — `@discordjs/opus` (музыка) и `sqlite3` (бан-таймауты) — собранные под конкретный ABI Node. Портативный Node в папке — это ровно та версия, под которую всё установлено, и `node.cmd` гарантирует, что `node .` возьмёт её. Любая другая версия даёт `Cannot find module '@discordjs/opus'` и музыки не будет (rest поднимется, `/play` — нет). Смена версии = переустановка зависимостей тем же Node (`npm install`); портативный Node не в git — у нового развёртывания prebuild встанет под его собственную версию.

## Настройка (первый раз)

1. Скопировать `config.example.json` → `config.json`. Если хочется по минимуму -- есть **`config.minimal.json`**: там ровно две вещи, без которых бот не работает вообще ("TOKEN" и блок сервера с единым "allow": true), а всё остальное бот берёт из значений по умолчанию (вписал токен и id сервера -- и всё)
2. Вписать свой `ID` (application id) и `TOKEN` (Bot → Reset Token)
3. Заполнить ID сервера/каналов/ролей (ПКМ по роли/каналу → «Копировать ID», включив режим разработчика в Discord). В `config.example.json` только плейсхолдеры (`ID_СЕРВЕРА`, `ID_ПОЛЬЗОВАТЕЛЯ_1` и т.д.) -- реальных id сервера и людей в шаблоне нет
4. **После любой правки `config.json` бота надо перезапустить**: id каналов/ролей читаются один раз при старте, и старый id останется в памяти (именно поэтому перенос глухого падал с `Could not resolve channel to a guild voice channel`, когда в конфиге уже был новый канал). Битые id бот теперь проверяет при старте и пишет: `[config] channel_common = ...: канала нет -- исправь config.json и ПЕРЕЗАПУСТИ бота`
5. **Интенты.** Бот запрашивает два привилегированных интента: **Server Members** (`"GUILD_MEMBERS": true` -- мгновенные вход/выход и полный список участников) и **Message Content** (`"MESSAGE_CONTENT": true` -- текст сообщений: команды `panda ...` и мост из пандалогии). Чего у приложения на самом деле нет, бот определяет **до входа**: спрашивает `GET /applications/@me`, смотрит флаги приложения и те привилегии, которых нет, **не запрашивает вообще** (иначе вход тратится на отказ `Used disallowed intents`); если что-то всё же откажут на входе -- снимет интент и переподключится. Бот обязан стартовать при **любом** наборе интентов, и об этом пишет прямо в лог (`[login] ... у приложения ОТКЛЮЧЁН -- запускаю без него`, `[intents] ...: да/НЕТ`). В портале сейчас включён только **Server Members** (Presence и Message Content выключены -- заявка только на нужный интент). Важно понимать: **полный список участников (List Guild Members) сам требует этого интента на уровне приложения** -- им и работает поллер; если Discord его отзовёт, вместе с поллером отвалятся вход/выход: приветствие новичку, таймаут за выход и возврат ролей. Чтобы это не было незаметно: бот скажет об этом при старте (`[poll] снимок участников НЕ ПОЛУЧЕН @ ...: нет доступа к списку (интент Guild Members)`) и дальше не чаще раза в 10 минут (`[poll] список участников не пришёл (...): проверь интент Guild Members`), а если список вдруг придёт **пустым или вразрез усохнет** -- тик пропускается, никого не записывают вышедшим и никому не выписывается таймаут (без этой защиты один сбойный ответ выглядел бы как «все вышли» и всем выписался бы таймаут, а перезаход -- бан). **Без интента доступны** (по документации Discord, «You Might Not Need a Privileged Intent»): один участник по id (`Get Guild Member`), поиск по префиксу (`Search Guild Members`), `Get User` и данные участника из самого слэш-взаимодействия -- на них можно переехать, если интент заберут (потеряв мгновенность вход/выход). Из непривилегированных используется **GuildModeration** -- он даёт журнал аудита для авторства действий (`кто замутил/перенёс`)

Зависимости уже стоят (`node_modules` в комплекте). Для чистой установки: `npm install` (+ вручную докачать бинарник yt-dlp: `node node_modules/youtube-dl-exec/dist/install.js`, и `@discordjs/opus` — prebuild).

## Что за каждый файл в папке (открыл папку и не помнишь, что это?)

| Файл / папка | Что это и можно ли трогать |
|---|---|
| `index.js` | **весь бот одним файлом.** Запуск -- `node .` (или ярлык/`node.cmd`), больше для работы ничего не нужно |
| `config.json` | **твои настройки и секреты:** токен бота, `db_key` (ключ шифрования базы), id сервера/каналов/ролей. В репозиторий **не попадает** (`.gitignore`). Потеряешь `db_key` -- зашифрованные записи базы не прочитаются: без ключа база бесполезна |
| `config.example.json` | шаблон конфига с комментарием к каждому ключу. Именно он лежит в репозитории, чтобы ничьи токены и id никуда не уехали. **Это же эталон по строкам:** при старте бот говорит, если боевой `config.json` от него отстал (v2.29) |
| `config.minimal.json` | самый короткий РАБОЧИЙ конфиг: только `TOKEN` и сервер с `allow: true` (без него бот сервер не обслуживает) -- ни `name`, ни `MUSIC`, ни `queue_page` там нет: всё это бот и так берёт из значений по умолчанию. Для быстрого развёртывания на чистом сервере: скопировать → `config.json`, вписать токен и id сервера; дальше добавлять настройки из `config.example.json` по мере надобности |
| `<id сервера>.sqlite` | **база включённого сервера** из `config.json`: роли для возврата, история наказаний, активные таймауты, очередь музыки. Один файл на сервер, значения зашифрованы AES-256-GCM (без `db_key` не читаются) |
| `<id сервера>.backup.sqlite` | ровно **одна** копия базы, перезаписывается при запуске, `node . backup` и по таймеру `backup_minutes` (не копится). Её дата совпадает с датой базы -- Windows сохраняет время файла при копировании, поэтому о свежести судить по дате нельзя: смотри строку `[db] базы:` в логе. Удалять можно -- создастся заново; но если удалить при живой базе, один запуск пройдёт без страховки |
| `<id сервера>.check-<дата>_<время>[-метка].sqlite` | **контрольные точки (v2.28):** отдельные снимки базы, сделанные командой `node . checkpoint`. В отличие от штатной копии, они НЕ перезаписываются -- именно чтобы вернуться к конкретному моменту (`node . restore <метка>`). Больше `backup_keep` штук не держим (по умолчанию 10, самая старая удаляется). Посмотреть список: `node . backups`. Зашифрованы ключом, который был при создании |
| `<id сервера>.broken.sqlite` | появляется **только** после `node . restore`: сюда откладывается побитая база, которую заменила копия. Тоже один файл |
| `<id сервера>.sqlite-journal` / `-wal` | остатки аварийного завершения (выдернули питание, закрыли окно жёстко). SQLite откатит сам, в логе будет пометка `был аварийный выход (журнал на диске -- SQLite откатит сам)`. Трогать не надо |
| `node_modules/`, `node-v24.21.0-win-x64/` | зависимости и портативный Node нужной версии (в git не идут) |
| `node.cmd` | «шим»: благодаря ему привычное `node .` **в этой папке** запускает бота на портативном Node, а не на системном (боту нужен Node 22+) |
| `README.md` | эта инструкция |
| `PRIVACY.md` | публичная политика конфиденциальности -- тот же текст, что лежит по адресу из `privacy_url` в конфиге (его показывают `/help` и `/mydata`). **Руками не правят:** файл собирается командой `node . privacy` из шаблона (в него подставляются ник владельца, название приложения, сроки хранения и значок ключа) |
| `privacy.template.md` | шаблон политики: текст + подстановки (`{{DATE}}`, `{{MARK}}`, `{{OWNER_NICK}}`, `{{SERVERS}}`, сроки хранения...). Правят шаблон, а не `PRIVACY.md`; значения «по умолчанию» (ник, название приложения) -- в шапке шаблона, она в публичный файл не попадает |
| `music_cache/` | **кэш аудио (v2.37, `MUSIC.cache`):** скачанные треки файлами (`<sha1 адреса>.m4a`). Это НЕ данные бота, а просто музыка -- папку можно удалить в любой момент, бот скачает заново; в базе про неё ничего нет. **Проигранное здесь не копится (v2.39):** файл отыгравшего трека удаляется сразу, остаются только играющий трек и предзагрузка (прежнее поведение -- ключ `MUSIC.cache_keep_played: true`). Верхний предел на всякий случай всё равно есть (`MUSIC.cache_max_mb`, по умолчанию 4096 МБ), папку можно увести в другое место ключом `MUSIC.cache_dir`. Недописанные хвосты (`.dl.`) убираются при следующем запуске. **Папка переносимая:** в имени файла только `sha1` адреса трека (никаких путей и записей в базе), поэтому её можно скопировать на другой диск или на другую машину -- готовые треки подхватятся сразу, без перекачивания (проверено стендом) |
| `images/` | 9 картинок из истории бота. Код их не использует -- оставлены как память о том, с чего начинали |
| `intents-request.md`, `intents-cheatsheet.md` | текст заявки на привилегированные интенты и шпаргалка к ней. В `.gitignore` (там id и цифры реального сервера) |
| `logs/` | **живой лог бота в файлах (v2.55):** `panda-ГГГГ-ММ.log` -- **файл на месяц** (это и есть ротация), те же строки с теми же метками времени, что в окне консоли. Сколько месячных файлов держать -- `log_keep_months` (по умолчанию 0 -- все), папку можно увести ключом `log_dir`. В `.gitignore` (там же правило `*.log`), поэтому в репозиторий лог не попадёт |
| `_*` (временные папки/файлы), `*.log`, `*.tmp` | рабочий мусор: в `.gitignore`, можно удалять |

**Файлов базы у ВЫКЛЮЧЕННОГО сервера нет.** Если в конфиге у сервера стоит `"allow": false`, бот ему базу не ведёт и файлов не создаёт (в памяти -- да, на диск -- ни байта). Если от прежних версий остались пустые `<id>.sqlite`/`<id>.backup.sqlite`, при старте будет одна строка:

```
[db] 396641596294299660 («БУНКЕР 13») выключен в конфиге (allow: false) -- базу ему не веду,
     а от прежних версий остались пустые 396641596294299660.sqlite и 396641596294299660.backup.sqlite (не нужны -- удали их)
```

Удалишь -- строка исчезнет и файлы больше не появятся. Включишь сервер обратно (`"allow": true`) -- база и копия создадутся сами, с нуля.

## Что умеет

- **Профильный статус бота:** виден везде, даже вне голосового. Играет музыку -- `Слушает: 🎶 Трек — «Канал» · в очереди 2 · в канале 4` (на паузе `⏸`, никого в канале -- `😴`), сидит без музыки -- `Смотрит: 🎧 «Канал» · в канале 4`, свободен -- `Играет: /help · /play · /join`. Название трека режется по лимиту поля (128 символов), а хвост с очередью и людьми остаётся. Обновлений не больше одного в 5 сек (лимит Discord на presence), текст берётся актуальный, повтор того же статуса не отправляется
- **Статус голосового канала:** пока бот сидит в канале, он пишет в его шапке, что играет (`🎶 Трек — 3:45`, на паузе `⏸`, а если никого нет -- `😴 нет слушателей: Трек`), сколько треков в очереди, сколько людей в комнате и сколько он там (`⏱ бот тут: 12 мин`). Обновляется по событиям (смена трека, очередь, вход/выход людей) и раз в минуту для счётчика времени; при выходе и при переезде в другой канал статус снимается с прежнего. Запросы к API склеиваются дебаунсом (не чаще раза в 3 сек), в лог идут только ошибки. Записи идут в Discord **по очереди** (своя очередь на канал), поэтому выход не может затереть уже отправленную строку -- в канале не остаётся устаревший статус. **Прочитать прежний статус канала Discord не даёт** (роут только пишущий, отдельного чтения нет -- проверено живым запросом: `405 Method Not Allowed`), поэтому «вернуть значение, которое было до бота» технически невозможно: вместо этого бот снимает СВОЙ статус при выходе и не переписывает чужой без изменения состояния. **Можно выключить совсем (v2.26):** `"MUSIC": { "channel_status": false }` -- бот не трогает шапку канала ВООБЩЕ (ни пишет, ни снимает): там остаётся только то, что поставил автор канала (в нашем `config.json` стоит `false`). Вся та же информация есть в **профильном** статусе бота -- `Слушает: 🎶 Трек — «Канал» · в очереди 2 · в канале 4`, и его видно везде, даже вне голосового. Свою прежнюю строку (если бота убили и он не успел её снять) можно убрать разово: `node . clearstatus <id канала>`; при выключенной настройке это единственное место, где бот вообще пишет в шапку
- **Владельцы каналов:** создав голосовой канал и получив права, участник становится владельцем: бот выдаёт ему SPEAK/MUTE/DEAF/MOVE, ставит тег 🔑 перед ником (и снимает, когда прав не остаётся; сверка догоняет теги после рестарта бота). Тег виден **сразу**, без перезахода в канал. Отдельная история (v2.15): без интента **GuildMembers** кэш ников не обновляется на смену ника, а `discord.js` при этом ещё и `fetch(id)` без `force` отдаёт **именно кэш** — поэтому свип каждые 45 секунд заново «ставил» уже стоящий 🔑 и писал ту же строку в лог (тот спам `[nick] +🔑 (sweep)`, который был виден в живом логе). Теперь ник читается из REST (`force: true`, по документации Discord этот одиночный запрос привилегированного интента не требует), а состояние читается свежим ТОЛЬКО когда оно неизвестно или расходится с правами: что бот поставил сам, он помнит в памяти процесса (`$nickSet`). Проверено стендом: первый свип ставит ключ одной строкой, второй и третий — молчат и в REST не ходят; Роли ADM/MOD (`role_admin`/`role_moder`) -- исключение: ключа у них не бывает (права есть всегда и все свои это знают), самодорисованный бот удаляет
- **Мут/глухота:** мут в чужом канале → оверрайд SPEAK:false + ЛС-уведомление + журнал; глухота в чужом канале → CONNECT:false + перенос в общий канал. **Общий канал `channel_common` -- это канал жалоб:** заходя туда, человек сразу размучивается и раздефливается (`подал апелляцию в ...` + запись 🆘 в журнал), чтобы мог сказать, за что его наказали. Пер-канальные запреты при этом остаются на своих каналах и возвращаются, как только он туда зайдёт («мут помнится по каналу»). Раньше эта ветка (в коде — `unMUTE for Appeal!`) была недостижима из-за раннего `return`: замученный заходил в общий канал и оставался замученным. Следствие: мут/глухота, выданные уже **внутри** общего канала, там же и снимаются (это и есть «жалоба»), а в остальных каналах наказания работают как раньше
- **Приветствие новичку (вернулось):** при входе на сервер бот пишет в личку приветствие, в котором **сам текст и картинка из сообщения с правилами** (`welcome_message` в канале `welcome_channel`), плюс ссылка на это сообщение (v2.17). Раньше в письме была **только ссылка**, и Discord рисовал её как название сервера -- выглядело так, будто текст потерялся. Нужны **оба** ключа, и это не прихоть: в Discord **нет способа найти сообщение по id без канала** (поиск есть только по тексту внутри канала), поэтому `welcome_channel` -- «где искать», `welcome_message` -- «что именно». Нет id сообщения -- в письме будет ссылка на канал; нет `welcome_channel` -- приветствие выключено целиком; сообщение не отдалось (удалили, нет прав) -- письмо уйдёт со ссылкой, как раньше, и в логе будет причина. **Ссылка может вести в другой (публичный) канал (v2.40, `welcome_public_channel`):** служебный канал с текстом правил часто закрыт (`#архивная`), и тогда в личке человек видел текст, но по ссылке получал «нет доступа». Ключ `welcome_public_channel` уводит **ссылку и название канала** в публичный канал (например «о сервере», куда обычно идут приглашения), а текст и картинки по-прежнему берутся из служебного сообщения; `welcome_public_message` (необязательный) -- ссылка на конкретное сообщение внутри него. В логе видно само событие и что попало в письмо: `[welcome] ЛС новичку <ник> отправлена (https://...) -- текст и картинки взяты из сообщения с правилами`; закрытая личка не ошибка бота -- в лог идёт причина. Перезаходы в таймауте приветствия не получают (у них другой путь -- бан-таймаут), а обычный возврат на сервер -- получает (бот не различает «новичок» и «вернулся»: истории входов у него нет, и с интентом Guild Members тоже -- он даёт только события, а не историю). **Задержка (v2.17):** с интентом Guild Members вход приходит мгновенно, без него -- опросом раз в 45 секунд (тогда письмо может прийти до минуты после входа; в журнале событие видно сразу). **Свой текст к правилам -- по желанию (v2.18, `welcome_prefix`):** по умолчанию (`true`) к тексту и картинкам из сообщения с правилами бот добавляет своё приветствие и краткое описание возможностей (`/play`, `/queue`, `/help`); `"welcome_prefix": false` -- в ЛС уходит ТОЛЬКО сообщение с правилами и ссылка на него, без описания бота. **Проверить глазами (v2.18):** слэш-команда `/welcome` -- бот пришлёт тебе ту самую ЛС (`/welcome user:@кто` -- другому, staff); в чате то же делает `panda welcome`, но она зависит от интента Message Content и после его отзыва перестанет работать, а `/welcome` -- нет.
- **Бан-таймаут:** выход с сервера → таймаут 20 мин (настраивается `onLeaveBanTimeout`); перезаход в течение таймаута → ЛС-предупреждение + бан до конца срока; при `onLeaveBanRealy: true` бан выдаётся сразу при выходе, при `false` -- только при перезаходе. **В логе и в ЛС -- ровно то, что сделано:** `участник X таймаут до ... (20 мин., бан -- только если вернётся раньше)` и `... таймаут истёк спустя 20 мин. (не вернулся)` против `участник X забанен до ... (20 мин., при выходе)` / `... забанен до ... (оставалось 0:03:20, перезаход во время таймаута)` у настоящих банов. Письмо «вам ограничен вход» перезаходящему уходит только когда бан действительно будет выдан (при `onEnterBanRealy: false` вместо письма в лог идёт `вернулся во время таймаута, но бан не выдан`), а запись таймаута с уже прошедшим сроком считается обычным входом (человек получает приветствие, а не письмо с прошедшей датой). Запись из базы снимается только ПОСЛЕ того, как бан реально снят: если снятие не удалось (права/сеть), бот помнит и повторит в следующем тике, а не потеряет человека в бане. Разбан автоматический, переживает рестарт бота (SQLite: время конца таймаута лежит в базе, `setTimeout` в памяти -- только чтобы снять вовремя). **Если бан не выдался** (у бота нет права «Банить участников», его роль ниже роли человека, сбой сети) -- наказание всё равно фиксируется: таймаут записывается в базу и в историю (событие «timeout»), а причина и что будет дальше -- в лог: `участник X НЕ забанен (бан при выходе не выдался): Missing Permissions [у бота нет права «Банить/Разбанивать участников» ИЛИ его роль стоит НИЖЕ роли человека -- проверь права роли бота] -- таймаут 20 мин. всё равно записан: вернётся раньше срока -- попробую забанить снова (onEnterBanRealy)`. Поэтому неудачный бан -- это не «ничего»: при перезаходе бот попробует выдать его снова, а таймер в конце срока не станет снимать бан, которого не было (`таймаут истёк спустя 20 мин. (бана не было -- снимать нечего)`). Если прав не хватает на снятие бана в конце срока, о причине пишется **один раз** (иначе спам раз в 45 сек), запись убирается с советом снять бан вручную, и то же самое делается для банов, поднятых из базы при старте. **Снять наказание вручную** — `/unban user:@кто reason:...` (админы/модеры): бот снимает и бан в Discord, и запись таймаута, и отложенный таймер разбана; кто снял и почему — в журнал, в лог (`[ban] <кто> снял наказание с <кого> (таймаут, срок был до ..., причина: ...)`) и в историю. Если бан снять не удалось (права/сеть) — бот НЕ чистит запись и не пишет ложной записи в журнал, а честно отвечает причиной
- **Без паузы между треками:** пока играет текущий, следующий уже готовится (`предзагрузка готова: ...`), поэтому следующая песня стартует сразу (`играю: ... (из предзагрузки, без паузы)`), а не после поиска и буферизации. Непригодившаяся заготовка глушится вместе с yt-dlp (при `/stop`, очистке очереди и выходе из канала) -- лишних процессов не остаётся. Если заготовка сломалась (видео удалили, сеть), трек просто берётся заново обычным путём
- **Музыка живёт файлом на диске, а не только в потоке (v2.37, `MUSIC.cache`, включено):** раньше звук шёл прямо из YouTube в Discord, то есть YouTube участвовал в проигрывании каждую секунду -- его сбои (`403`, `Broken pipe`, оборванный сет) слышали слушатели, а перемотка и продолжение после перезапуска каждый раз заново просили звук у сервиса. Теперь бот **качает аудио на диск и играет его оттуда**. Короткий трек (до `MUSIC.cache_full_max_min` минут, по умолчанию 15) скачивается целиком ДО старта -- и обычно этого даже не видно, потому что он качается предзагрузкой, пока играет предыдущий (`предзагрузка готова (уже на диске): X`); зато перемотка (`/seek`, кнопки ±30 с) мгновенная и точная, а после перезапуска трек продолжается с той же секунды без сети. Длинный сет и любой прямой эфир играют сразу потоком, но тот же звук **параллельно пишется в файл**: доиграл до конца -- файл остался готовым, и со следующего раза (перемотка, восстановление, повтор) трек берётся с диска (`играю: X (с диска)`). Папка по умолчанию -- `music_cache/` рядом с ботом (`MUSIC.cache_dir`, можно полный путь), **на диске лежит только то, что звучит сейчас (v2.39):** файл отыгравшего трека убирается сразу после перехода (`кэш: убрал N файлов (M МБ)`), остаются играющий трек и предзагрузка -- за долгий вечер кэш от этого не растёт. Прежнее поведение (файлы живут до лимита и уходят по старости -- удобно слушать один плейлист по кругу) включается ключом `MUSIC.cache_keep_played: true`; сам лимит `MUSIC.cache_max_mb` (по умолчанию 4096 МБ; играющий и готовый следующий не трогаются; `0` -- без лимита) остаётся страховкой в обоих случаях. **Кэш не может сломать музыку:** не скачалось, папка недоступна, место кончилось -- бот пишет причину в лог и играет потоком как раньше; выключается одним ключом `"MUSIC": { "cache": false }`. Удалить папку можно в любой момент -- в базе про неё ничего нет, бот скачает заново (в логе это видно: `качаю на диск: X`, `сохранил на диск: X (10 МБ)`)
- **О проблеме с треком узнают ДО эфира, а убирается он только по факту (v2.41 + v2.43, `MUSIC.queue_check`):** раньше единственным местом, где выяснялось «видео больше нет», была предзагрузка — человек ждал свою песню, чтобы узнать, что её не будет. Теперь бот сам прочёсывает очередь от начала и предупреждает заранее, а автору говорит в тот канал, откуда трек добавили (v2.39), одним сообщением на канал. **Но из очереди он теперь НИЧЕГО не убирает:** приговор зависит от НАШЕГО IP и прокси (регион, VPN) и легко меняется — владелец поменял прокси, и трек, «мёртвый» пять минут назад, спокойно играет. Поэтому проверка только **помечает** трек (⚠ в списке `/queue`, счёт «под вопросом») и пишет в канал автора «Из очереди не убираю — проверю, когда дойдёт»; уходит трек ровно по факту: не запустился при воспроизведении — тогда и убирается с настоящей причиной (и это видно в отчёте). Если пометка не подтвердилась (трек заиграл), бот снимает её сам и пишет об этом в лог. **Итог проверки виден прямо в `/queue`** — строка `🔎 Проверка очереди заранее: просмотрено 18 (в 01:09), ⚠ под вопросом: 1, убирать не стал, убрано при воспроизведении: 0; ещё 6 треков -- проход примерно через 2 мин`; когда проверять нечего, так и написано («всё проверено»). Размер страницы этот блок учитывает, поэтому из-за него треки из `/queue` не пропадут. **Про лимиты YouTube (главный вопрос владельца):** сначала идёт дешёвый oEmbed (один крошечный запрос, без скачивания и плеера), и только по его отказу запускается yt-dlp — подтвердить приговор тем же инструментом, который бы играл трек; **передний край очереди (3 трека) спрашивают сразу у yt-dlp** — oEmbed отвечает «есть» и про видео, закрытое для этого IP по региону, а такое не сыграет; за проход не больше `queue_check_depth` треков (по умолчанию 20) с паузой `queue_check_gap_ms` (по умолчанию 5 с), один и тот же адрес за сессию проверяется один раз, прямые эфиры не проверяются вообще. Живой прогон 20.09.2026 на боевом сервере (тогда ещё с удалением): `проверка очереди: проверено 18 треков -- мёртвых убрано: 1` — закрытый по региону DJ-сет выявился **за несколько минут до того, как до него дошло бы дело**. Именно этот случай и показал, почему удалять заранее нельзя: владелец меняет прокси, и такой трек потом играется спокойно (теперь на этом месте строка `проверка очереди: проверено 18 треков -- под вопросом: 1 (из очереди не убрал)`).
- **Долгие плейлисты больше не зависят от качества сети:** трек лежит на диске, поэтому "сел интернет посреди сета" больше не означает обрыв у слушателей; а та же самая запись пригодится второй раз -- повторный `/play` того же трека/сета играет практически мгновенно и с любой секунды
- **Бот НИЧЕГО не забывает (очередь, текущий трек, место в треке, канал):** всё лежит в базе (SQLite), сохраняется на каждом изменении, раз в 20 сек и **в момент Ctrl+C**. Отдельная важная правка: в keyv v5 строка-URI больше не подгружает адаптер — `new Keyv('sqlite://...')` молча уходил в память, и база на диск не писалась вообще (баны не переживали перезапуск). Теперь адаптер передаётся явно (`@keyv/sqlite`), ошибки базы видны в логе строкой `[db] ...`. Очередь не «устаревает» по времени: после перезапуска, падения или `/leave` бот помнит её сколько угодно. **Забывает её только `/stop`** -- и ещё естественный конец очереди (когда она доиграла до конца живым слушателям: `[music] очередь доиграна до конца`). Восстановление: после падения бот заходит в тот же канал **сразу** (и остаётся там, даже если очередь пуста — присутствие хранится отдельной записью, `musicState/voice`, v2.24), а музыку включает, как только там появится живой слушатель (`очередь ждёт слушателя`); **с v2.34 в пустую комнату он не играет даже первый трек**: слушатели проверяются ДО старта, бот заходит и молчит (`зашёл в «Канал» и МОЛЧУ: живых слушателей нет ... начну, как только кто-то войдёт`), а очередь и место в треке остаются нетронутыми; после `/leave` сам не лезет -- ждёт `/join` (`очередь с прошлого раза на месте (выходили по /leave) -- ... ; продолжу по /join`). Продолжает с того же места (`возобновляю очередь в «Канал»: Трек (с 1:24) + ещё 3 в очереди`), сдвиг запрашивается даже с 1 секунды и даже если до конца оставалось 15 сек. **Продолжение с места: маленький сдвиг -- сразу своим ffmpeg, большой -- сначала секцией с проверкой (v2.35).** Измерено живым опытом на настоящем DJ-сете (это и был случай из лога, где возобновлённый сет замолкал через пару секунд): `--download-sections` на таких источниках отдаёт **ноль байт** и падает через 30-45 секунд (`ERROR: ffmpeg exited with code 4294967274`), а раньше проверка ждала всего 1.5 с и принимала пустышку за рабочий поток. Теперь сдвиг до 2 минут делается **сразу своим ffmpeg** (`-ss`: звук -- через ~5-6 с, при сдвиге 110 с -- ~10 с), а на больших сдвигах секция пробуется с проверкой: пришёл ли хоть один байт за 8 с (`секция с 1:00:00 ничего не отдала за 8 с -- беру тот же трек через ffmpeg`). Адрес, на котором секция не сработала, до конца работы бота больше не пробуется. Если не вышло совсем -- трек берётся с начала (`продолжение с 01:24 не удалось -- беру трек с начала`). У прямого эфира позиции нет, поэтому он всегда начинается live, как и раньше
- **Обрыв связи/потока не бросает трек:** если yt-dlp отвалился посреди песни, бот возвращает трек в очередь и продолжает его **с места обрыва** (`поток оборвался (на 00:42, ...) -- продолжаю тот же трек, попытка 1/3`), а не перескакивает дальше. Три попытки подряд -- тогда пропускает и пишет в канал `⚠️ ... пропускаю` (чтобы не биться в мёртвый источник бесконечно). Обрыв голосового соединения (`Disconnected`) тоже не теряет очередь: `[music] вышел из «Канал» (очередь сохранена, обрыв связи: Трек ждёт, 3 далее)`, и бот вернётся сам, когда в канале будет кто-то живой. **Отдельно -- видео, которого больше нет (v2.35):** удалённое или закрытое видео (`ERROR: [youtube] ...: Video unavailable`) бот называет прямо в логе сразу (`видео больше нет на YouTube (...) -- уберу из очереди, когда дойдёт`), помечает трек и **убирает его из очереди сразу, как только очередь до него дойдёт** -- без четырёх неудачных попыток yt-dlp (как и просили: «пропускать сразу, а не биться»). Убирается одной строкой в лог (`видео больше нет на YouTube (проверено предзагрузкой): ... -- убрал из очереди`) и сообщением в канал (`🗑 «...» -- видео больше нет на YouTube, убрал из очереди`); если в очереди были только такие треки, бот ведёт себя как при пустой очереди. Раньше в логе оставалась голая причина без контекста, а трек пропадал молча. Проверки «не бот» и возрастные ограничения -- НЕ этот случай (они зависят от IP и могут пройти через прокси позже)
- **Музыка не играет в пустоту:** если в канале не осталось **живых слушателей** (боты и сам бот не считаются), трек ставится на паузу (`в «Канал» никого -- пауза`), в статусе и профиле -- `😴 нет слушателей: Трек`. Как только кто-то зашёл -- продолжает с того же места (`слушатель вернулся в «Канал» -- продолжаю`). Ручная `/pause` при этом не ломается: уход и возврат слушателей её не отменяют. **Кто такие «живые слушатели» (v2.34):** боты не считаются, даже когда Discord не прислал нам `member` для чужого голосового состояния (такой бот раньше считался слушателем, и бот играл в комнату с одним чужим ботом); спорное состояние спрашивается у Discord напрямую, а если тот не ответил -- считаем, что человек есть (лучше заиграть живому, чем промолчать). Ожидание видно и в профиле: `⏸ «Канал» — жду слушателя` (а не `🎧`, как будто музыка идёт)
- **Кто первый -- тот и прав:** `/play` добавляет трек в конец очереди. Если бот уже играет живым слушателям в другом канале – не переезжает, DJ просто пополняет очередь (`🎧 Играю в «...» -- там и продолжу`); если бот сидит один -- переезжает к тому, кто позвал. **`/join` тоже больше не перехватывает бота силой (v2.18):** если бот играет трек и его **автор сидит в той же комнате** (то есть бот поёт именно для него), другой DJ команду получает с отказом (`🎧 Не перееду: я играю **Трек** в «...» для автора трека (Лахуля)`) -- увести можно только честно: `/skip`, `/stop`, когда автор сам уйдёт или когда дойдёт до трека другого автора. Если автора в комнате нет -- `/join` работает, а если при этом в старой комнате оставались живые слушатели, бот прямо об этом напишет (`🎧 В «...» оставались слушатели -- теперь они без музыки`) и оставит строку в логе: DJ видит последствие своих действий. Правило одно для всех, у кого есть права DJ/админ/модер, и в логе видно автора: `[music] (кто: DJ) /join отклонён: играю для автора трека Лахуля в «Комната¹»`. **Стоять в голосовом канале не обязательно:** DJ может набирать плейлист откуда угодно, бот заиграет по `/join` (пока пишет `⏳ Я не в канале -- заиграю, когда позовёшь /join`). Позвал `/join` в канал, где нет музыки -- подберёт очередь и продолжит с места
- **Бот играет там, где слушает автор трека (v2.18):** тот, кто добавил трек, ставит его для себя -- поэтому если автор трека сидит в голосовом канале, в момент старта этого трека бот **переезжает к нему** и остаётся там до трека другого автора (или до `/leave`), а если до трека того же автора дошло ещё раз -- он уже там. Автора в голосовом нет -- бот не двигается; сам он по-прежнему **никогда** не заходит и не выходит: переезд возможен только когда он уже где-то играет. Сразу после явного `/join`/`/play` (5 секунд) бот тоже не уезжает -- иначе он уехал бы от того, кто его только что позвал. Причина видна в логе: `[music] перешёл в «Канал²» -- автор трека Лахуля слушает здесь`, а выбранный канал запоминается (`savedChannelId`), поэтому после перезапуска бот продолжает там же. Тот же смысл и у паузы: если бот стоит **один** (в комнате никого -- `😴`), а автор музыки зашёл в другую комнату, бот переезжает к нему и продолжает с того же места (`здесь никого, а автор трека ... слушает здесь`) -- кто поставил трек, тот его и слушает. Приоритет -- у автора **недоигранного** трека (он сейчас и играет), а если тот уже ушёл -- у автора **следующего** в очереди: иначе пауза запирала бы бота в пустой комнате и трек следующего автора не начался бы никогда. **v2.27:** бот смотрит **вперёд по всей очереди**, а не только на текущий и следующий трек (на длинном чужом плейлисте нужный автор может быть и десятым), и это срабатывает на **любой** паузе, а не только на «нет слушателей»: если человек поставил `/pause`, а комната опустела, бот тоже не остаётся там, где его никто не слышит (пауза -- хороший момент пересмотреть, где он нужнее, потому что нового события в голосовых может и не быть). **v2.28: пауза -- вообще не препятствие для переезда**, потому что смысл переезда -- играть тому, кто слушает: раз бот приехал туда, где есть человек, он там и играет (паузу снимает, включая поставленную человеком -- он же пришёл слушать музыку, а не тишину). Плюс **v2.28: режим «не ждать отсутствующих авторов»** (`"MUSIC": { "skip_absent_author": true }`, по умолчанию включён): если бот стоит ОДИН и молчит, а дальше в очереди есть треки тех, кто слушает прямо сейчас в другой комнате, треки отсутствующих (вместе с недоеденным текущим) уезжают **в конец очереди** (ничего не теряется -- вернётся автор, и его треки снова дойдут по очереди, порядок внутри них сохраняется), а бот переезжает к тому, кто есть, и играет. В канал уходит понятное сообщение (`⏭ 2 трека от тех, кого нет в голосовом, -- ждать некому: поставил их в конец очереди и играю ...`), в логе -- строка с названиями пропущенного. `false` -- как раньше: ждём, пока автор вернётся. Переезд делается один раз на событие (бот не бегает между двумя авторами туда-сюда), а если в комнате есть хоть один живой человек -- бот никуда не двигается вообще. Это и есть ответ на «тащить бота руками»: тот же путь работает для **Stage-каналов (сцена)** -- бот туда заходит, но Discord не даёт ему вещать, пока он не спикер, поэтому в лог идёт подсказка `«Сцена» -- Stage-канал: чтобы музыку было слышно, Stage Moderator должен сделать бота спикером`
- **Объявление и ЛС без интента Message Content (v2.18):** `/announce text:... file:... channel:...` (staff) публикует объявление **от имени бота** (по умолчанию -- в тот канал, где вызвали), `/dm user:@кто text:...` (только админы) отправляет человеку личное сообщение, а **правый клик по сообщению -> «Переслать в общий»** (staff) пересылает чужое сообщение в общий канал -- с текстом и вложением. Всё это берёт данные из самой команды, поэтому интент Message Content им **не нужен** (Discord сам советует такой путь в гайде «You Might Not Need a Privileged Intent»), и это работающий запасной вариант, если интент отзовут: заявка на него в этом смысле больше не критична. У «Переслать в общий» есть важная осторожность: оригинал удаляется **только в канале-источнике** моста (`pipe_channel_source`) -- если staff переслал сообщение откуда-то ещё, оно остаётся на месте (удалять чужое сообщение по одному клику нельзя), и в ответе это сказано прямо. Отправка у меню и у старого моста -- **одна и та же функция** (`relayPipe`), так что порядок «сперва отправка, потом удаление» и передача вложений ссылкой одинаковы. В логе видно авторство: `[pipe] (кто: Admin) переслал сообщение Лахуля -> #общий + вложение: ... (оригинал удалён)`
- **Что бот помнит о человеке -- `/rolecheck user:@кто` (v2.17, админы/модеры):** отчёт по одному человеку: есть ли он сейчас на сервере и какие роли у него сейчас; что лежит в памяти о его ролях (`save_roles`: дата записи, полный список, что именно **вернётся при входе**, что вычеркнуто и почему -- «уже есть» / «исключена в config» / «роли больше нет на сервере», и предупреждение, если запись старше `save_roles_days`); текущее наказание с точным сроком и причиной; история за окно (`выходов 2, таймаутов 1, банов 1, снятий 1`). Команда работает **и для того, кто не на сервере**: всё лежит в базе по id, а для проверки самого человека хватает одиночного REST-запроса («Get Guild Member»), которому интент Guild Members не нужен. Теперь то же самое -- командой **`/history`** (для всех, как `/queue`): кто, когда и что поставил, с видом добавленного -- **трек, прямой эфир или целый плейлист** со составом (первые три названия и «и ещё N») и счётчиком эфиров в пачке. История живёт **отдельно от очереди** (запись `musicState/history`): её не стирают `/clear` и `/stop`, она переживает перезапуск, в ней остаётся и уже доигранное. Сколько пачек помнить -- ключ `MUSIC.history_len` (по умолчанию 25, максимум 200, 0 -- выключить), а сколько ТРЕКОВ суммарно -- `MUSIC.history_tracks` (по умолчанию 500, максимум 5000, 0 -- без этого лимита): без второго лимита пачка из 50 треков вытесняла бы из истории пять одиночных заходов, а вместе они режут историю по-честному -- пачка уходит **целиком**, от самой старой, новейшая не выбрасывается никогда. **v2.56: у каждой пачки видна её судьба и откуда она** -- вторая строка «↳» говорит, сколько треков ещё ждёт в очереди (или «в очереди уже нет (доиграно или убрано)», а если трек пачки звучит -- «▶ сейчас в эфире»), показывает, **что человек написал в `/play`** (ссылку, адрес плейлиста или запрос -- это можно вставить заново, не разыскивая трек), и две короткие прямые ссылки на сами треки (длинные адреса не печатаются: обрезанная ссылка бесполезна). Судьба считается по видео-id треков, а не по названиям: одноимённых песен у одного автора бывает много. Если настоящей истории ещё нет, а в очереди есть треки с метками добавления (первый запуск после обновления), бот ОДИН РАЗ переносит эти пачки в историю и пишет об этом в лог -- очередь при этом не меняется, а треки из старых баз (без метки) в перенос не попадают
- **Роли между перезаходами (v2.14, `save_roles`, по умолчанию ВКЛЮЧЕНО):** выходя с сервера, человек больше не теряет роли -- бот запоминает их (ключ -- id участника) и при возврате **добавляет недостающие**. Раньше это умел только сторонний бот; теперь это делает сама PANDAMIA, и **одновременно с другим ботом-хранителем ролей**: бот только добавляет и никогда ничего не снимает (у кого роль уже есть -- не трогает), так что «кто первый успел, тот и вернул», и права гарантированно на месте. В базу не попадают @everyone, роли интеграций (managed) и уже удалённые роли; свой список исключений -- `save_roles_exclude`, срок хранения -- `save_roles_days` (**по умолчанию НАВСЕГДА: `0`**; задано число -- записи старше него убирает свип). Выключить: `"save_roles": false` у сервера. **Точность (v2.16):** роли хранятся не «как бог на душу положит», а ровно на момент выхода -- снимок поллера бывает до 45 секунд старым, поэтому правки ролей, случившиеся после снимка, достраиваются по журналу аудита: роль, снятая за секунды до выхода, в базу НЕ попадёт и не вернётся при входе, а выданная за секунды до выхода -- попадёт. Если возвращать нечего -- старая запись стирается (иначе она воскресила бы уже потерянную роль). Рядом живёт аналогичная настройка истории наказаний: `bans_history_days` (**по умолчанию тоже НАВСЕГДА: `0`**) — окно сводки в `/bans`: за годы видно, кто перезаходит и сколько раз был наказан; задано число -- старые события убирает свип
- **Видно, кто в наказании и кто как наказывался (v2.14–v2.15):** `/bans` (только админы/модеры, ответ виден вызвавшему) показывает всех, у кого действует таймаут/бан: имя, что это (🚫 бан или ⏳ таймаут -- проверяется по списку банов Discord), точный срок снятия (`снимется 18.09.2026, 21:04:33 (через 00:03:20)`) и причину из аудита. Ниже — **сводка** за окно `bans_history_days` (по умолчанию -- **за всё время**, `0`; задано число дней -- «за N дн»): `• **Кто** -- выходов 3, таймаутов 2, банов 1, снято 1 _(последнее: 18.09.2026, 21:04:33)_`. События пишутся сразу, как происходят (выход, таймаут, бан, снятие — в том числе вручную через `/unban`), окно истории настраивается, а при хранении «навсегда» свип историю не трогает вообще. Снять наказание досрочно — `/unban`. Вызов любой команды, как и все остальные, попадает в лог
- **Громкость песен не «прыгает» (v2.14, `MUSIC.normalize`, включено):** записи сведены с разной громкостью, поэтому раньше одну песню хотелось пригромче, другую потише. Теперь между yt-dlp и Discord стоит свой ffmpeg с фильтром `loudnorm` (`MUSIC.filter`), который приводит песни к одному среднему уровню -- команды и настройки не нужны. Фильтр проверяется один раз при старте (в логе: `выравнивание громкости: включено -- loudnorm=...`); если сборка ffmpeg его не умеет или в конфиге `normalize: false` -- играем как раньше, музыка из-за этого не встаёт
- **Процессы за собой убираются (v2.14, важный фикс):** `player.stop()` в @discordjs/voice НЕ закрывает поток трека, поэтому после каждого `/skip`, `/stop` и `/leave` процессы yt-dlp и ffmpeg оставались висеть в памяти. Теперь у играющего трека есть ссылка на его поток, и он глушится при любом конце трека (доиграл, пропустили, остановили, вышли) -- лишних процессов не остаётся
- **Бота можно тащить руками (v2.14):** если админ перетащит бота из комнаты в комнату, это видно в логе (`[music] бота перенесли: «Канал¹» -> «Канал²»`), статус с прежнего канала снимается, а пауза/продолжение работают по обычному правилу слушателей: в новой комнате никого -- пауза (`😴`), зашёл человек -- продолжает с того же места
- **Прямые эфиры:** `/play` со ссылкой на трансляцию работает и помечается отдельно -- 🔴 в статусе канала и профиле, `Длина: 🔴 LIVE` в ответе и очереди (у эфира длительности нет). У обычного трека, для которого YouTube не отдал длину, теперь `--:--`, а не «LIVE» -- раньше эти два случая не отличались. Перезапуск эфир не перематывает (перематывать там нечего) и теряет только те секунды, что бот не работал

ничего не выбрасывается. **v2.56: у команды два режима** -- «Срочный переход» (по умолчанию, ничего не теряется: прерванный трек встаёт в конец очереди с той же секундой) и «Обрезать до трека» (всё до него убирается насовсем -- прежнее поведение; это чистка одним движением, поэтому и только для staff)), `/move number to` (у DJ -- только СВОИ треки и только на свои же места: цель должна быть занята его треком, иначе отказ; staff -- любые), `/seek time` (v2.32 -- перейти внутри текущего трека: `83`, `1:30`, `1:02:03`; Меню автора (v2.32) показывает **всех** авторов одинаково всем -- права проверяются при действии, и отказ всегда называет причину; в нём два действия: **«⬆ Поднять наверх»** (все треки автора -- выше остальных) и **«🗑 Убрать его треки»**. - **Мост серверов (pipe):** сообщение человека в `pipe_channel_source` (пандалогия) пересылается в `pipe_channel_target` (общий чат) **от имени бота**, затем оригинал удаляется. Пересылается и текст, и **вложения** (картинки/файлы): раньше объекты вложений передавались в Discord как есть и терялись, из-за чего на сообщение-картинку бот отвечал `50006 Cannot send an empty message` -- теперь вложения передаются ссылкой, а файл без текста пересылается как файл. Порядок именно такой (сперва отправка, потом удаление) -- при ошибке отправки сообщение остаётся в источнике, а не пропадает. Требует интента **Message Content**: без него Discord присылает событие с пустым текстом, и бот ничего не пересылает и ничего не удаляет (в логе: `[pipe] ... НЕ переслано`). - **Инструкция (`/help` и `panda help`):** тот же текст, что приходит в стартовой ЛС. `/help` — слэш-команда, доступна всем и сразу (без DJ-роли и без голосового канала), ответ виден только вызвавшему; `panda help` — бот присылает её в ЛС (сама команда из канала убирается). Один источник текста на все три входа — `/help`, `panda help` и стартовая ЛС. В тексте есть всё новое: `/bans`, чистка очереди по автору, кнопки листания и контакты владельцев. **Что показывать (v2.36, уточнено в v2.42):** адрес политики задаётся **только верхним ключом** `privacy_url` -- один на всех, у сервера своего адреса нет (иначе у одного бота было бы несколько разных политик при одной базе). А вот **показывать ссылку или нет решает каждый сервер сам**: `"show_privacy_url": false` внутри блока сервера скрывает её там, не убирая адрес из конфига (удобно, пока бот, например, проходит проверку привилегированных интентов). Верхний `show_privacy_url` -- только значение по умолчанию для тех серверов, у которых своего флага нет; если он неверного типа (строка вместо `true`/`false`), сервер ошибётся в `[config]`, а не подхватит неожиданное значение. У сервера нет и не может быть своего `privacy_url`: если его там написать, он молча ничего не делает -- теперь и об этом есть строка в `[config]`. Контакты "владелец хостинга" (`show_owner_hoster`) и "владелец сервера" (`show_owner_server`) как и раньше включаются/выключаются каждым сервером отдельно (по умолчанию включены; если оба скрыты, в помощи будет "администрации сервера"); всё описано в `config.example.json`
- **Сводка для staff:** `/bans` (кто в наказании + история), `/unban user:@кто reason:...` (снять досрочно), `/rolecheck user:@кто` (что бот помнит о ролях и наказаниях человека и что вернёт при входе), `/forget user:@кто` (удалить сохранённые о человеке роли, историю и треки из очереди), `/welcome [user:@кто]` (послать себе или человеку проверочное приветствие), плюс объявления и ЛС -- `/announce text:... file:... channel:...` (staff) и `/dm user:@кто text:...` (админы), плюс правый клик по сообщению -> «Переслать в общий» (staff). Права: первые три -- админы/модеры, `/dm` -- только админы; ответ везде виден только вызвавшему, а сам вызов попадает в лог
- **Команды в чате:** `panda ping`, `panda help`, `panda file`, `panda test`, `panda welcome [@юзер]` (посмотреть приветствие новичка -- в v2.18 у этого появился слэш-близнец `/welcome`, работающий без интента Message Content), `panda dm @user текст` (админам; теперь то же самое удобнее слэш-командой `/dm`, которая НЕ требует интента Message Content, -- текстовая команда осталась как привычный путь). `panda dm` принимает и упоминание, и просто id (`panda dm 123456789012345678 текст`); команду бот удаляет **только после успешной отправки**, а если ЛС не ушло -- пишет причину в канал и в лог (раньше в этом случае была полная тишина, а команда всё равно удалялась). `panda test` -- самопроверка: бот пишет ЛС тому, кто её вызвал (никаких зашитых id в коде нет)
- **Что бот поднял из базы (v2.14):** при каждом старте в лог идёт строка про баны/таймауты, причём всегда -- даже когда наказаний нет: `[ban] из базы поднято 0: активных банов/таймаутов нет -- никто не наказан` или `[ban] из базы поднято 2 активных (1 бан, 1 таймаут): Должник до 18.09.2026, 21:04:33 (осталось 00:03:20, бан) | ...; просроченных записей: 1 -- сниму сейчас`. Это ровно то, что нужно после перезапуска: видно, не наказал ли кого бот за время, пока он не работал (раньше это приходилось выяснять только по журналу Discord). Сроки везде точные, до секунды
- **Что значит «убрал N записей» в логе (v2.17):** это про **срок хранения**, а не про потерю данных. Свип (раз в 45 сек и при старте) удаляет из базы то, что старше окна, и пишет это явно: `[ban] истёк срок хранения истории 30 дн (bans_history_days): удалено из базы 2 записи -- событий в них уже не было, активные наказания не тронуты` и `[roles] истёк срок хранения 30 дн (save_roles_days): удалено из базы 1 запись о ролях -- эти роли всё равно не вернулись бы (запись просрочена)`. **По умолчанию удалять нечего (v2.18):** оба ключа -- `0` = хранить всегда, и тогда этих строк в логе не бывает (а записи без даты, оставшиеся от старых версий, убираются всегда -- по ним всё равно нечего вернуть). Активные таймауты, баны и свежие записи о ролях не трогаются: окно настраивается (`bans_history_days`, `save_roles_days`)
- **При старте** бот шлёт ЛС с инструкцией списку людей из `STARTUP_DM` (v2.22: это отдельная настройка и больше ни на что не влияет -- просто уведомление «бот запустился»; список может быть пустым, можно указать и один id строкой, а не списком). Контакты в тексте помощи настраиваются: `OWNER` (верхний ключ) -- владелец **хостинга** бота, тот, кто его запускает; `owner_server` (у сервера) -- владелец **сервера**. Это разные люди, и каждый показывается своим флагом (`show_owner_hoster` / `show_owner_server`); если ничего не указано, в помощи останется «администрации сервера». **`OWNER` и `STARTUP_DM` независимы (v2.22):** раньше пустой `OWNER` подменялся первым id из `STARTUP_DM`, из-за чего контакт в помощи (и право на `/rekey`) доставалось тому, кто просто подписан на ЛС о запуске. Теперь нет: адрес для связи -- только `OWNER`, а список получателей стартовой ЛС -- только `STARTUP_DM`, и любой из них можно не заполнять. Так в коде нет ни одного зашитого id, и репозиторий можно отдавать людям
- **Проверить приветствие на себе (v2.18):** `/welcome` -- бот пришлёт в ЛС ровно то приветствие, которое видят новички (удобно править `welcome_message` и сразу смотреть результат, кэш не мешает); `/welcome user:@кто` -- то же на конкретном человеке (доступно staff). В чате осталось и привычное `panda welcome [@юзер]`, но она держится на интенте Message Content, а `/welcome` работает без него. Событие попадает в лог: `[welcome] проверка: <кто> -> <кому> -- с текстом и картинкой из сообщения с правилами`
- **Удалить сохранённое о человеке -- `/forget user:@кто` (v2.18, staff):** бот убирает из своей базы всё, что накопил по этому человеку: роли для возврата (`memberRoles`), историю наказаний (`banHistory`) и добавленные им треки в очереди музыки -- **включая играющий и ждущий**: если сейчас играет его трек, он снимается и прерывается, «ничейного» не остаётся (v2.26), а в ответе пишет, что именно удалил (или что удалять было нечего). **Активное наказание при этом не трогается** -- оно снимается `/unban` (это действие модерации, а не «хранение данных»), и в ответе об этом сказано прямо. Стоит в одном ряду с «не хранить лишнего»: данные и так лежат только локально в `*.sqlite` и не уходят никуда, а команда закрывает вопрос «как человеку запросить удаление своих данных» -- он есть в заявке на привилегированные интенты
- **Шифрование сохранённых записей (v2.20, ключ `db_key`):** значения в базе (`memberRoles`, `banHistory`, `membersBanTimeout`, `musicState`, `channelsBusy`) пишутся в виде **AES-256-GCM** («конверт»: iv + тег + шифртекст), а ключ лежит в `config.json` в строке `db_key` -- 64 hex-символа или парольная фраза (фраза превращается в ключ через scrypt, одинаково при каждом запуске). Новый ключ выдаёт команда `node . keygen` (`node.cmd keygen` в папке бота). Ключа нет или он пуст -- бот работает как раньше, открытым текстом, и при старте честно пишет об этом: `[db] шифрование записей: выключено (нет db_key в config.json)`; при включённом -- `[db] шифрование записей: ВКЛЮЧЕНО (db_key), AES-256-GCM -- не потеряй config.json: без ключа записи не прочитаются`. **Старые записи читаются как есть** (формат распознаётся по префиксу `enc1:`), поэтому включение шифрования ничего не теряет: история ролей, счётчики наказаний и очередь остаются на месте. Больше того -- при каждом старте с ключом бот **один раз переводит накопленные записи в шифрованный вид**: `[db] перевёл на шифрование 3 записи от прошлых версий -- открытого текста в базе больше нет`. Функция идемпотентна (повторные запуски ничего не делают, без `db_key` -- тоже ничего), ключи записей не меняются, значения остаются теми же -- меняется только вид на диске. Смысл простой: ответ «данные зашифрованы» относится ко **всему** содержимому базы, а не только к тому, что появилось после включения ключа.
- **«Что бот помнит лично обо мне» -- `/mydata` (v2.22):** каждый человек сам может посмотреть, что о нём лежит в базе: роли, которые вернутся при входе (с датой записи и сроком хранения), историю наказаний (выходы/таймауты/баны/снятия и первое-последнее событие), активный таймер выхода, свои треки в очереди, а также итог «сколько записей и сколько весит» и то, чего в базе **не бывает никогда** (текстов и истории сообщений, ников, e-mail, IP и т.п.). В конце -- как это удалить (`/forget`) и ссылка на политику (`privacy_url` в конфиге, а если её нет -- строки просто нет). Ответ **виден только вызвавшему**; о другом человеке -- только админ/модер (иначе это была бы разведка чужих данных), и в этом случае в отчёте пишется «не о тебе». В логе остаётся факт обращения: `[data] (кто: Lapulya) посмотрел, что бот помнит о ... -- отчёт выдан`.
- **Смена ключа шифрования -- `/rekey` (v2.22, ТОЛЬКО владелец бота):** одна команда перешифровывает всю базу одним новым ключом. Команду видит только тот, у кого есть права администратора, а выполнить может лишь владелец -- id из ключа `OWNER` (остальным отказано даже с админкой; если `OWNER` не заполнен, команда недоступна никому). Что происходит: каждая запись расшифровывается известным ключом, шифруется новым и **сразу проверяется чтением обратно**; нечитаемые записи не трогаются и честно считаются в отчёте. Новый ключ **сам вписывается в `config.json`** (`db_key`) -- перезапуск не нужен, а потерять ключ из‑за забывчивости не получится; тот же ключ печатается **в консоль** (в Discord он не отправляется: оттуда ключ ушёл бы на серверы Discord) -- сохрани его отдельно, без него записи не читаются. Если перешифровка почему‑то прервалась, новый ключ **не** становится основным: в `config.json` остаётся старый `db_key`, а новый лежит рядом в `db_key_prev`, поэтому уже переписанные записи читаются даже после перезапуска, и `/rekey` можно спокойно повторить. Если база была открытой (`db_key` пуст), `/rekey` просто **включает** шифрование на уже накопленных данных. Границы честные (и описаны в `PRIVACY.md`): ключ лежит **рядом с базой**, поэтому копия папки целиком остаётся читаемой -- защищён другой случай, когда утекает **только файл базы** (бэкап, облако, копия на другую машину): внутри нечитаемый мусор, а не список id ролей и наказаний. Ключ в git не попадает (`config.json` в `.gitignore`), но и терять его нельзя: без ключа уже зашифрованные записи не читаются -- бот при этом не падает, а пропускает их и пишет в лог, что не смог расшифровать
- **Лог (окно бота) -- только события**, без периодического шума: вход/выход/переход по голосовым каналам, микрофон/наушники/стрим/камера, создание и удаление каналов, музыка (`[music] играю: ...`), слэш-команды и `panda ...` (`[cmd]`). Если в конфиге битый id -- при старте будет строка `[config] ...`; если не удался перенос глухого участника -- `[voice] перенос ...`. Остальное молчит. Повторов одного и того же в логе нет: свип ключей 🔑 больше не переписывает ту же строку каждые 45 секунд (v2.15) — строка `[nick] +🔑` появляется только когда тег **реально** изменился, и тогда же делается один запрос к API. Каждая строка -- одна строка: ошибки yt-dlp пишутся одной строкой с причиной из его же stderr (`[music] yt-dlp завершился: ERROR: [youtube] ...: Video unavailable`), без команды и многострочной простыни. У запуска трека тоже одна строка: `[music] играю: Название (из предзагрузки, без паузы)` -- раньше рядом появлялась отдельная `предзагрузка сыграла: ...`, которую по логу читали как «прошлый ролик отыграл» (v2.14). Если процесс ffmpeg выравнивания громкости умрёт на середине, будет одна строка с причиной, без падения бота -- и коды выхода теперь расшифрованы: не `код 3199971767`, а `код -1094995529 (ffmpeg: не смог прочитать поток)`. А когда бот глушит поток **сам** (`/skip`, `/stop`, `/leave`, конец очереди), такой строки нет вовсе: это не событие, а шум от собственного действия. **У каждой строки лога есть метка времени (v2.30):** раньше часть сообщений (ошибки yt-dlp и ffmpeg, сбои прав, непереданные ЛС) печаталась в обход общего вида строки и стояла в живом логе без времени -- теперь `console.log`/`console.error` обёрнуты один раз, и штамп получает любая строка, у которой его ещё нет (CLI-команды `dump`/`files`/`privacy`/`backup` печатают как раньше, без времени). Длинные строки режутся по **слову**, а не посередине (`...Error opening input files: In` больше не бывает). И строка `[music] бота выключили/выкинули` больше не появляется после собственного выхода бота: `/stop` и `/leave` -- это мы, о них уже сказано строкой `вышел из «...»` (а вот чужой кик по-прежнему видно). У мутов/глухоты/переносов указывается ещё и **автор** (`кто: ...`): Discord не присылает его в голосовых событиях, поэтому он берётся из журнала аудита (интент **GuildModeration** -- НЕ привилегированный, одобрения не требует; нужен право «Просматривать журнал аудита», при приглашении с `permissions=8` оно есть). **Тот же лог лежит и в файле (v2.55):** при запуске бота (`node .`, без аргументов) все строки идут ещё и в `logs/panda-ГГГГ-ММ.log` -- **файл на месяц**, с теми же метками времени. Это нужно ровно для двух вещей: окно консоли прокручивается (а разбирать случай приходится позже), и лог можно просто открыть, пока бот работает -- файл пишется синхронно, поэтому актуален в любой момент. Состав тот же, что в консоли: стартовые `[db]`/`[music]` тоже там есть (в файл их пишет «зеркало», которое включается сразу после чтения конфига, а обёртка со штампом времени его дополняет -- поэтому ни одна строка не попадает в файл дважды). Папка по умолчанию -- `logs/` рядом с ботом (`log_dir`, можно полный путь), сколько месячных файлов держать -- `log_keep_months` (по умолчанию `0` -- не удалять ничего; задано число, например `6`, -- при смене месяца старое уходит, и об этом есть строка в логе). Папка `logs/` и любые `*.log` в `.gitignore`, так что **в репозиторий лог не попадёт**; файл не открылся (права, диск) -- одна строка в консоль, и бот работает дальше. **Сервисные команды в лог не пишут:** `node . dump`, `node . unkey`, `node . backup` и прочие -- это не работа бота, и в `dump` лежит содержимое базы, а в `unkey` -- открытый текст, поэтому при любом аргументе в консоль всё идёт как раньше, без файла.

## Интенты: что доступно сейчас и что будет 9 октября 2026

Бот старается жить на непривилегированных интентах, но две вещи без них не сделать: **Message Content** (текст сообщений -- команды `panda ...` и мост из пандалогии) и **Guild Members** (события входа/выхода и полный список участников, из которых растут приветствие новичку, таймаут за выход и возврат ролей).

Важное открытие (v2.17): **полный список участников по REST -- это ровно та возможность, которую даёт Guild Members**. То есть «работа без интента» последние версии была только на бумаге: список приходил потому, что приложение этим интентом уже владеет. Поэтому интент теперь запрашивается явно (`"GUILD_MEMBERS": true`), вход/выход ловятся мгновенными событиями, а опрос раз в 45 секунд остался **резервным** путём (бот был выключен -- переходы добираются опросом; интента нет -- работает только он, и в логе будет строка об откате). Один и тот же переход не обрабатывается дважды: отметка «уже разобрано событием» живёт 5 минут, иначе только что вошедший в следующем тике выглядел бы как вышедший и получил таймаут.

**Старт при любом наборе интентов (v2.25).** Раньше откат по интентам был только на бумаге: `client.options.intents` в discord.js -- **замороженный** `IntentsBitField`, поэтому `.remove()` молча ничего не делал, бит оставался, вход снова падал `Used disallowed intents` -- и бот не запускался вообще (поймано живым запуском сразу после того, как в портале сняли Message Content). Теперь интент снимается **подменой битфилда**, а обе привилегии проверяются заранее по флагам приложения: нет флага -- просим без него. Проверено и стендом на реальной функции, и живыми запусками: (1) в портале оставлен только **Server Members** -- бот стартует, вход/выход и список участников работают; (2) `"GUILD_MEMBERS": false` (имитация отзыва) -- бот стартует, в отчёте `Guild Members: НЕТ`, а музыка, ключи 🔑, статусы и журнал аудита работают как обычно.

При каждом старте в лог идёт отчёт **по факту**, а не по настройке:

```
[intents] 🐼PANDAMIA🐼 | Message Content (текст сообщений, команды "panda ..."): да
[intents] 🐼PANDAMIA🐼 | Guild Members (мгновенные вход/выход): да
[intents] 🐼PANDAMIA🐼 | полный список участников (REST): да -- 11608 участников (от него зависят вход/выход, таймаут за выход и возврат ролей)
[intents] 🐼PANDAMIA🐼 | журнал аудита (авторство мутов/переносов): да
```

Плюс одна строка про **все** серверы сразу (включая те, где бот есть, а в `config.json` его нет): `[login] приложение в 2 серверах, участников суммарно ~11745 (🐼PANDAMIA🐼 ~11608 | Старый ~137)`. Число людей приходит вместе с каждым сервером (`memberCount` в событии GUILD_CREATE), поэтому «сколько нас всего» видно прямо в логе -- без похода в портал и без интентов.

Про 9 октября 2026 (письмо от 10.09.2026, срок продлён до этой даты): по документации Discord порог считается **не по числу серверов, а по числу уникальных пользователей, которые могут видеть приложение**. На одном твоём сервере 11 608 участников -- порог в 10 000 уже превышен, поэтому привилегированные интенты нужно подтверждать **запросом в Developer Portal**; без одобрения 9 октября их заберут. Это не ломает запуск: бот стартует без интента (в логе `[login] Discord запретил интент ... -- переподключаюсь без него`), но теряется ровно то, что на них держится:

| Возможность | Без Guild Members | Без Message Content |
|---|---|---|
| Вход/выход: приветствие новичку, таймаут за выход, возврат ролей | **нет** (нет ни событий, ни списка) | есть |
| `panda ...` в чате, мост из пандалогии (pipe) | есть | **нет**, но есть `/announce` и «Переслать в общий» |
| Музыка, мут/глухота, ключи 🔑, статусы, `/bans`, `/rolecheck` | есть | есть |

### Как устроено ревью (по документации Discord от 10.06.2026)

- Порог считается **по уникальным пользователям, которые видят приложение** (не по числу серверов). Уведомление даётся, когда порог 10 000 превышен **и** какой-то привилегированный интент включён или его пытаются включить -- как раз наш случай.
- На подачу заявки -- **90 дней** с даты уведомления (в письме от 10.09.2026 срок продлён до **9 октября 2026**). Пока заявка на рассмотрении, приложение **работает как обычно и может входить на новые серверы**. Заявку можно подать и позже -- доступ просто потеряется до одобрения.
- **Проверка личности владельца для этого не требуется:** ревью смотрит на назначение бота, а не на паспорт. Отдельная верификация с документами -- это другой процесс (для приложений, которые хотят стоять в 100+ серверах).
- Что смотрит ревью: конкретное назначение; просьба **только нужных** интентов (Presence нам не нужен, и мы это подчёркиваем); как бот обходится с данными (что в памяти, что хранится и сколько). Готовый текст заявки -- `intents-request.md`, в репозиторий он **не попадает** (там id реального сервера, файл в `.gitignore`). К нему есть **шпаргалка на одну страницу** -- `intents-cheatsheet.md` (адрес формы, поле→что вписать, список скриншотов, чек-лист перед отправкой, что делать при отказе) -- тоже вне репозитория.
- Про приветствия в гайде Discord сказано буквально: «Мои приветственные сообщения перестали работать» -> **Fix: Enable and request the Guild Members intent** -- то есть это один из признанных поводов для интента, а не «на всякий случай».
- **Публичная политика конфиденциальности (это не формальность):** в форме есть вопрос «У вас есть общедоступная политика конфиденциальности…?». По опыту других разработчиков отказ прилетает именно за него: заявку вернули с формулировкой «политика должна лежать по **постоянному публичному адресу** и описывать ваши практики работы с данными» -- то есть варианта «Нет» на практике нет, хотя форма его предлагает. Готовая политика лежит в репозитории -- `PRIVACY.md` (что хранится, где, сколько, как удалить; период хранения описан с учётом конфига: роли и счётчики по умолчанию без срока давности, срок включается ключами `save_roles_days` / `bans_history_days`). Её нужно выложить в постоянный адрес (публичный репозиторий или gist) и в форме поставить **Да** + ссылку.
- **Шифрование данных «на диске»:** гайды (MEE6, Invite Tracker) советуют отвечать на этот вопрос **Да** -- и у нас это правда: значения в базе шифруются AES-256-GCM (`db_key`), старые записи бот переводит в шифрованный вид сам при старте, ключ меняется командой `/rekey`, а посмотреть базу можно только чтением (`node . dump`, на диск ничего не расшифровывается). Поэтому в форме -- **Да**; границы честно описаны в `PRIVACY.md` и в `intents-request.md` (Блок F).
- **Что именно публиковать (важно):** файл `PRIVACY.md` уходит в публичный адрес целиком, поэтому в нём не должно оставаться ничего «для владельца» -- ни служебных заметок в HTML-комментариях (они всё равно видны в исходнике), ни заглушек вроде `example.com`. Всё такое держим здесь, в README: например, решение про **второй контакт**. Discord-ника достаточно, а если захочешь адрес для тех, кто вообще не в Discord -- заведи ящик **только для бота** (НЕ личный: он станет публичным), впиши его строкой в раздел `Contact` и не забудь, что он попадёт в публичный документ.
- **Ещё одна мелочь, за которую могут вернуть заявку:** постоянную ссылку на политику стоит вписать не только в поле формы, но и в портале приложения на вкладке **General Information** -> **Privacy Policy URL**: тогда она видна прямо в профиле бота, и видно, что политика существует не «на словах».
- **«Храните данные API 30 дней или меньше?» -> «Нет»** -- это нормальный ответ (так отвечает и MEE6): у нас намеренно долго живут роли и счётчики, об этом есть пояснение в заявке (`intents-request.md`, Блок D).

### План Б: что делать, если интенты всё-таки заберут

Заявка -- путь A. Путь B (жить без интентов) выглядит так, и он у нас частично уже готов:

| Что теряется | Почему нельзя без интента | Что можно сделать |
|---|---|---|
| Мост из пандалогии, команды `panda ...` | Discord присылает события с пустым `content` | **Сделано:** `/announce`, `/dm` и «Переслать в общий» (правый клик) -- всё из самой команды |
| Приветствие новичку в ЛС | Нет ни `GUILD_MEMBER_ADD`, ни списка участников | Автоматически -- никак (Discord прямо советует для этого интент). Остаётся `panda welcome` для проверки текста и указатель на `/help` в правилах |
| Таймаут за выход | Нет событий входа/выхода | **На частичных данных:** member-объект приходит в **голосовых событиях и взаимодействиях** (это НЕ привилегированные интенты), а в нём есть `joined_at` и список ролей. Значит можно вести память «когда я последний раз видел человека и какие роли у него были» и ловить перезаход по изменившемуся `joined_at` -- наказание догонит человека при первом же его действии (зашёл в голос или вызвал команду), а не мгновенно |
| Возврат ролей | Списка участников нет | Одиночный запрос «Get Guild Member» **без интента работает** (раздел «You Might Not Need a Privileged Intent»); роли можно запоминать в момент **любого** наблюдения человека (голос/команда) и возвращать при следующем наблюдении |
| Общий счёт "кто-то вышел" | Списка нет | `approximate_member_count` из обычного `GET /guilds/<id>?with_counts=true` -- это не интент: видно, что число упало, а вот **кто** -- только по частичным данным выше |

Честная оговорка к таблице: колонка «Что можно сделать» -- это **план**, а не то, что уже работает. В коде на сегодня готовы строки «Сделано» (`/announce`, `/dm`, «Переслать в общий», `/welcome` для проверки текста) и то, что и так живёт на непривилегированных интентах (музыка, мут/глухота, ключи 🔑, статусы, `/bans`, `/rolecheck`, `/forget`). Механика «частичных данных» (помнить человека по голосовым событиям и взаимодействиям, ловить перезаход по изменившемуся `joined_at`, возвращать роли при первом же действии) -- только спроектирована: она делается отдельной правкой, если интент действительно заберут.

Практический вывод: если вход/выход и возврат ролей нужны -- имеет смысл подать запрос в Developer Portal (форма Privileged Intents) и описать назначение (модерация голосовых каналов, возврат ролей). В коде предусмотрено оба варианта: любой интент можно выключить в `config.json` (`"GUILD_MEMBERS": false`, `"MESSAGE_CONTENT": false`) -- бот отработает без ошибок и честно скажет об этом в логе.

## Комментарии в конфиге

В JSON комментариев не бывает, поэтому подсказки лежат **обычными ключами с окончанием `_comment`** (идея владельца): код их не читает, JSON остаётся валидным, а понять, что куда вписать, можно прямо в файле.

```json
"log_channel_comment": "Текстовый канал-журнал: вход/выход, мут/глухота, музыка.",
"log_channel": "804684593684152330",
"onLeaveBanRealy_comment": "false -- при выходе бан не выдаётся, только запоминается срок.",
"onLeaveBanRealy": false
```

Отдельно при старте печатается **`[config]`-аудит**: настройки, которые молча ничего не делают -- пары ключей (`welcome_message` без `welcome_channel`, `temp_lobby` без `temp_category`, источник моста без приёмника), бессмысленные сочетания (таймаут за выход с выключенными `onLeaveBanRealy` и `onEnterBanRealy`), непохожие на id роли и `owner_server`, отсутствующий `allow` у сервера, `PREFIX` без пробела на конце. Если всё настроено правильно -- не печатается **ни одной** такой строки.

Важная деталь: **внутри `SERVERS` ключ -- это id сервера**, поэтому подсказки внутри блока называются так же (`"470047648112705546_comment"`), а бот при загрузке выкидывает всё, что не похоже на id (и молчит про `_comment`). Если в `SERVERS` попадёт странный ключ, в логе появится строка `[config] ключ "..." в SERVERS -- не похож на id сервера -- пропускаю его`. Верхний ключ `_ПРО_КОММЕНТАРИИ` -- тоже просто подсказка. **Заготовка из `config.example.json`** (`"ID_СЕРВЕРА"`) распознаётся ОТДЕЛЬНО -- это не ошибка того, кто только что скопировал шаблон: вместо «странного ключа» бот пишет `[config] в SERVERS осталась заготовка (ID_СЕРВЕРА) -- вместо неё впиши id своего сервера`, а если рабочих серверов не осталось -- честно говорит, что запустится, но делать ничего не будет.

## Настройка: исторические ключи

В `config.json` могут остаться ключи от старых версий -- код их не читает, можно удалить. Уже удалены как мёртвые: `admins` (админов определяют роли `role_admin`/`role_moder`), `log_channel_temp` (второй журнал), `afkLikeChannels`, `logo`, а также `ERROR` и `NOTICE` (v2.23 -- были объявлены в коде, но не читались нигде: флаги не влияли ни на что). ## Обновление кода и перезапуск

Что проверено на живом стенде (и почему состояние не теряется):

- **очередь, текущий трек, место в треке и канал живут в `*.sqlite` в папке бота**, а путь к базе строится от `__dirname` (папка модуля), а не от текущей папки. Значит любой способ запуска -- ярлык, `node .`, `node.cmd` из другой рабочей папки -- пишет и читает **одну и ту же** базу; APP-режим `node.cmd` ещё и сам делает `pushd "%~dp0"`, так что «Рабочая папка» в ярлыке может быть любой;
- **обновление кода (`git pull`, переключение веток, правка `index.js`)** базу не трогает: `*.sqlite` в `.gitignore`. После перезапуска бот поднимает очередь из неё же (`возобновляю очередь в «Канал»: Трек (с 1:24) + ещё 3 в очереди`);
- **после перезапуска в пустом канале бот молчит, а не играет (v2.34):** он заходит в тот же голосовой канал и ждёт человека (`зашёл в «Канал» и МОЛЧУ: живых слушателей нет ... начну, как только кто-то войдёт`), очередь и место в треке остаются нетронутыми, и музыка стартует с той же секунды, как только кто-то зайдёт (или по `/join`). Если живой слушатель в канале уже есть -- играет сразу;
- **`Ctrl+C`** сохраняет сразу (`сохраняю очередь перед выходом...`, не дольше 1.5 с) -- очередь и секунды позиции уходят в базу. Дальше cmd.exe спрашивает `Завершить выполнение пакетного файла [Y/N]` -- это вопрос **оболочки**, а не бота: бот в этот момент уже сохранился и вышел;
- **пока играет трек**, позиция дописывается каждые **5 секунд** (у позиции нет событий -- только таймер), а очередь и все переходы (`/play`, `/stop`, `/leave`, смена трека) -- сразу по событию;
- **при закрытии окна крестиком** Windows убивает процесс без сигнала, поэтому последние секунды позиции могут потеряться (очередь и трек к этому моменту уже в базе) -- максимум 5 секунд. Хочешь точнее -- `Ctrl+C`;
- **не запускать `git clean -xfd`** в папке бота: он сотрёт всё, что в `.gitignore`, то есть **базу с очередью и портативный Node** (`node-v*`). Чистая копия без последствий -- это `git stash`/`git checkout` или просто `git pull`;
- **смена версии Node = переустановка зависимостей** (`npm install` тем же Node): от ABI зависят `@discordjs/opus` (музыка) и `sqlite3` (вся база). Старый Node (например через `nvm use 16`) даёт `Cannot find module '@discordjs/opus'` и не пишет в базу -- поэтому и не убираем `node.cmd`.
- **роли и кнопки очереди (v2.16)** тоже проверены стендом на реальном `index.js`: роль, снятая за секунды до выхода, не возвращается при входе (и по gateway-событию журнала, и по REST-запросу) -- при этом роль, выданная перед выходом, сохраняется, а если возвращать нечего, старая запись стирается; пустой или сбойный список участников не превращается в «все вышли» (никому не выписывается таймаут); кнопки под `/queue` ставят/снимают треки с теми же номерами, что `/remove`, отбивают не-DJ и не дают листать чужую очередь.
- **очередь по 15 треков (настраивается), стрелки «⬆/⬇», `/rolecheck` и интенты (v2.17)** проверены стендом на реальном `index.js`: страница собирается в пределах лимита сообщения (длинные названия срезаются, номера второй страницы продолжаются); «⬆/⬇» переставляют трек с теми же номерами, что `/move` (включая края: на первом месте «⬆» заблокирована), не-DJ отбивается, играющий трек не перезапускается, предзагрузка переезжает, а очередь в базе не сбивается; мгновенное событие и опрос не обрабатывают один переход дважды; `reportIntents` показывает реальное состояние интентов; `/rolecheck` печатает роли, «вернётся при входе» и наказания -- в том числе для человека не с сервера.

## Хранилище: почему keyv + SQLite

Базы `*.sqlite` (keyv поверх SQLite) -- сознательный выбор, и менять его **не нужно**:

- зависимости уже стоят и собраны (`sqlite3` -- native, в комплекте с портативным Node), новая библиотека = переустановка зависимостей на всех развёртываниях;
- данные лежат **локально в папке бота**, без сервера и интернета -- бот работает и без сети, никакие внешние сервисы не упадут;
- объёмы тут микроскопические (записи о таймаутах, роли, одна очередь музыки), поэтому «быстрее/мощнее» (Postgres/Redis/Mongo) даст только лишние хлопоты: их надо где-то поднимать и беречь;
- важный момент, который уже учтён: в keyv v5 конструктор со строкой-URI **молча уходит в память**, если адаптер не передан явно (`store: new KeyvSqlite(...)`) -- из-за этого база одно время вообще не писалась на диск. Если когда-нибудь менять хранилище, эту ловушку надо проверять так же: записать → выйти → прочитать заново.

Альтернативы на будущее (ждем, пока появится реальная потребность): `better-sqlite3` напрямую -- быстрее и без слоя keyv, но требует нативных сборок; `node:sqlite` -- встроен в Node 24, но его API ещё меняется. Ни одна из них не даст ничего, что было бы видно в работе бота.

## Посмотреть, что лежит в базе (только чтение)

Шифрование (`db_key`) сделано так, что записи на диске нечитаемы, а «просто очистить `db_key`» -- **ловушка**: зашифрованные записи не расшифруются (бот их просто пропускает), а новые начнут писаться открытым текстом, то есть часть данных при этом перезапишется в открытом виде. Смотреть в базу нужно так:

```bash
node . dump                     # все серверы: сколько записей (открытых/зашифрованных/нечитаемых) и их содержимое
node . dump 247110936115150848  # только записи одного человека
```

Файл базы открывается **read-only** (ни один байт не меняется, бот при этом не запускается), значения расшифровываются ключами из `config.json` (`db_key` и `db_key_prev`) и печатаются по-человечески: роли и когда записаны, история наказаний по видам, активные таймауты (с остатком времени), очередь музыки. Записи, зашифрованные неизвестным ключом, не ломают вывод: про них пишется `зашифровано, но ни одним ключом из config.json не открывается`. Нужен Node 23+ (встроенный `node:sqlite`) -- портативный Node в папке бота подходит; бот при этом спокойно работает, читать базу можно на ходу.

Как **включить/вернуть** шифрование: `node . keygen` → вписать ключ в `db_key` → перезапуск (бот сам переведёт открытые записи в шифрованный вид и напишет `[db] перевёл на шифрование N записей`). Смена ключа -- `/rekey` (только владелец бота).

## Все консольные команды (одним списком)

Ключи трогаются **только из консоли** -- в Discord есть одна ключевая команда (`/rekey`, и она лишь меняет ключ, ничего не стирая). Всё остальное -- здесь, в папке бота (можно через `node.cmd`):

```bash
node .                          # запустить бота (живой лог)
node . help                     # список ВСЕХ консольных команд (то же печатается на опечатку)
node . keygen                   # напечатать НОВЫЙ ключ (64 hex) для строки db_key
node . files                    # что за каждый файл в папке и что можно удалять (+ примеры команд)
node . cache                    # кэш музыки: что скачано, сколько занимает, что можно удалить
node . cache --clear            # стереть кэш целиком (бот скачает заново; данные бота не трогаются)
node . cache --prune            # убрать из кэша самое старое по лимиту MUSIC.cache_max_mb
node . dump [id]                # посмотреть базу глазами (read-only, бот не запускается)
node . backup                   # обновить штатную копию базы и проверить, что она читается
node . checkpoint [метка]       # сделать контрольную точку (отдельный файл с датой в имени)
node . backups                  # что есть: база, штатная копия и все контрольные точки
node . restore [метка]          # вернуть базу из штатной копии или из конкретной точки
node . clearstatus <id канала>  # разово снять свою строку из статуса голосового канала
node . privacy                  # пересобрать PRIVACY.md из шаблона (имена спросит у Discord)
node . privacy --offline        # то же, но без сети: имена берём из шапки шаблона
node . privacy --check          # только проверить, разошлись ли PRIVACY.md и шаблон (ничего не пишет)
node . fixauthors <id> [имя] [--dry]   # проставить автора трекам без автора (--dry -- только показать)
```

**v2.32: `node . fixauthors`** -- треки из старых версий автора не помнят, а без автора обычный DJ не может с ними ничего сделать. Команда проставляет автора всем таким трекам (id -- кому записать, имя -- необязательно, для журнала): `node . fixauthors 123456789012345678 fantazer._.`; с `--dry` только показывает, сколько записей затронется, и ничего не пишет. Если такие треки есть, бот говорит об этом сам при старте.

**v2.33: `node . help`** -- список консольных команд теперь можно спросить, а не угадывать: раньше его печатала только ошибка про опечатку, и `node . help` отвечал «Неизвестная команда: help». Список ОДИН на оба случая (и на `node . help`, и на опечатку) и начинается с самого `node .` -- то есть видно, что без команды стартует именно бот. `node . unkey` в списке нет сознательно (это «красная кнопка», о которой в документации не пишут: команда работает, если набрать её точно).

**v2.27:** любая другая строка после `node .` теперь **не запускает бота**, а даёт ошибку со списком команд (раньше `node . nokey` или опечатка в `node . dum` молча поднимали бота -- лишний процесс вместо понятного ответа). **Рабочую базу в открытый текст бот не расшифровывает никогда** и команды «очистить `db_key`» нет; «просто убрать `db_key` из config.json» -- та самая ловушка выше, так делать не надо.

**v2.29: `node . privacy`** -- публичная политика конфиденциальности больше не правится руками. Половина того, что в ней написано, живёт в других местах: название приложения и ник владельца -- в Discord, серверы, таймаут и сроки хранения -- в `config.json`, значок ключа 🔑 -- в самом коде. Поэтому текст лежит шаблоном `privacy.template.md` с подстановками, а сборка -- одной командой. Так файл и разошёлся раньше (в нём стояло старое название приложения, а руками такое не замечаешь):

```bash
node . privacy            # собрать PRIVACY.md: спросит у Discord название приложения и ник владельца
node . privacy --offline  # без сети (значения -- из шапки шаблона)
node . privacy --check    # разошлись ли файл и шаблон; код возврата 1, если да (удобно перед публикацией)
```

Команда печатает, откуда взято каждое значение, и **отказывается писать файл**, если в шаблоне осталась подстановка без значения (лучше понятная ошибка, чем дырка в публичном тексте). Шапка-инструкция из шаблона в `PRIVACY.md` не переносится -- в публичном файле никакого мусора. Копию по ссылке (`privacy_url`, например gist) обновляют вручную: команда об этом напоминает, а `--check` показывает, разошлась ли она с шаблоном.

**v2.29: боевой `config.json` больше не отстаёт от примера молча.** Подсказки и новые ключи живут в `config.example.json`, а в боевой файл их никто не переносит сам -- так `backup_keep` и оказался только в примере. Теперь при старте бот сравнивает ключи (верхний уровень, `MUSIC` и каждый рабочий сервер -- с блоком `ID_СЕРВЕРА` из примера) и пишет, чего не хватает:

```
[config] в config.json нет 7 строк из config.example.json -- сервер 470047648112705546 («🐼PANDAMIA🐼»): allow_comment, name_comment, ...
[config] это строки-подсказки (_comment) и ключи со значениями по умолчанию: без них бот работает, но значения берёт из кода, а не из примера
```

Когда всё на месте -- ни одной строки. Выключенные серверы (`allow: false`) не разбираются: у них и id рабочих нет.

**v2.28: `node . files`** -- открыл папку и не помнишь, что это за файл? Одна команда печатает таблицей каждый файл и папку: размер, дата изменения, что это и **можно ли удалять** (например, `.backup.sqlite` -- можно, создастся снова; `<id>.sqlite` -- НЕТ, там всё). В конце -- список всех консольных команд **с примерами аргументов**. Команда только читает: ничего не создаёт, не меняет и не удаляет.

## Резервная копия базы и защита от запуска с побитой базой

База (`<id сервера>.sqlite`) -- единственное место, где живут роли, история и очередь, и пострадать она может не от бота, а от резкого выключения ПК, обрыва питания, диска или антивируса. Поэтому рядом всегда лежит **одна** копия (`<id>.backup.sqlite`): она не копится, а перезаписывается.

- при **каждом запуске** база проверяется (`PRAGMA integrity_check`), копия обновляется, и в лог идёт одна строка: `[db] базы: 470047648112705546 («🐼PANDAMIA🐼») -- 42 записи, копия обновлена`. Время копии -- это время изменения файла (видно в проводнике);
- **v2.27: пока бот работает, копия обновляется и сама** -- раз в `backup_minutes` (по умолчанию **60 мин**, `0` -- как раньше: только при старте). Это важно именно для долгих запусков: без этого копия оставалась с момента старта, а в ней не было ни новых ролей, ни истории, ни очереди. Новых файлов при этом **не появляется** (имя всё то же, копия перезаписывается), а в лог попадает только изменение или ошибка: `[backup] плановая копия обновлена (3 -> 4 записи)`. Ничего не изменилось -- ни строчки (иначе за сутки набралось бы 24 одинаковых);
- если база **побита** (обрезана, забита мусором, повреждена диском) или в ней **0 записей, а в копии они есть** -- бот **не запускается** и печатает, что делать (код возврата 1). Это защита от худшего сценария: «поработать с пустой базой и постепенно затереть живые данные»;
- копия обновляется при **каждом** нормальном запуске, в том числе когда записей стало **меньше** (вернулся человек -- запись ролей больше не нужна, `/forget` стёр роли и историю, таймаут истёк): в логе это видно как `копия обновлена (было 2 -- записи уменьшились)`. Раньше уменьшение останавливало обновление, копия отставала и при восстановлении возвращала бы уже ненужное. Не тронуть копию бот может ровно в одном случае -- когда в базе **0 записей, а в копии они есть** (это уже потеря данных, и на нём бот вообще не стартует);
- `node . backup` -- сделать и проверить штатную копию вручную (это **не** «именованная точка», а тот же самый файл: у копии нет имени/даты); `node . restore` -- вернуть базу из копии: текущую откладывает рядом как `<id>.broken.sqlite` (тоже один файл, перезаписывается);
- **v2.28: контрольные точки** -- отдельные файлы `<id>.check-<дата>_<время>[-метка].sqlite`, чтобы вернуться к конкретному моменту (перед большой чисткой, перед сменой ключа, просто «на всякий случай»):
  - `node . checkpoint [метка]` -- сделать точку сейчас (метка необязательна и попадает в имя: `checkpoint before-cleanup`); файл создаётся так же проверенно -- через временный файл и с чтением обратно;
  - `node . backups` -- одной таблицей: что в базе сейчас, что в штатной копии, какие есть точки (число записей, размер, дата) и чем их возвращать;
  - `node . restore <метка>` -- вернуть базу ИЗ ТОЧКИ (метка -- часть имени: `before-cleanup` или просто `2026-09-19`; `node . restore` без метки -- из штатной копии, как раньше). Если метка подходит к нескольким точкам или ни к одной -- бот ничего не трогает и перечисляет, что есть;
  - **перед подменой базы** бот сам делает страховочную точку текущего состояния (`...-before-restore.sqlite`) -- если восстановили не то, есть куда вернуться;
  - точек на сервер хранится не больше `backup_keep` (по умолчанию **10**, `0` -- не удалять старые вовсе); когда появляется новая сверх лимита, удаляется **самая старая по времени** (метка в имени на порядок не влияет -- на этом стенд поймал реальный баг);
  - автоматически по расписанию точки **не создаются** -- в папке не появляется ничего, чего бы владелец не попросил;
  - **про ключ:** файл точки зашифрован тем ключом, который действовал при её создании. После смены ключа (`/rekey`) старая точка читается только если прежний ключ остался в `db_key_prev` -- иначе записи в ней не расшифровать.
- копия всегда проверяется **чтением** (целостность + совпадение числа записей с базой), а копирование идёт через временный файл -- неудачная копия не может подменить целую;
- если рядом лежит `<id>.sqlite-journal` (остался от аварийного завершения) -- в строке будет пометка `был аварийный выход`: SQLite откатит сам, вмешиваться не надо;
- проверка пропускается только на старом Node без `node:sqlite` (бот тогда работает как раньше -- не проверять лучше, чем не работать).

Работать в папке бота с незапущенным ботом -- нормально: `backup`/`restore`/`dump` печатают отчёт и **выходят**, не запуская второго бота.

## Снять свою строку из шапки канала

```bash
node . clearstatus 1414754348139020359   # id голосового канала
```

Нужно ровно один раз и только в одном случае: если бот писал статус в шапку канала, а потом процесс убили (закрыли окно, выдернули питание, `taskkill`) -- выйти красиво он не успел, и строка осталась в канале. Discord этот роут **только пишущий** (прочитать, что там сейчас, нельзя), поэтому команда просто снимает статус с указанного канала. При `MUSIC.channel_status: false` это единственное место, где бот вообще пишет в шапку. Команда ничего не запускает и выходит сама.

## Git

`config.json`, базы и зависимости уже в `.gitignore`. Начало работы:

```bash
git init
git add .
git commit -m "PANDAMIA bot v2.2.3"
```

**Процесс обновлений:** изменения готовит Codebuff и **сам оформляет коммит**;
владелец смотрит `git log` / `git show` -- и **push делает сам** (`git push`).
Так в репозитории всегда лежит восстановимая история: любой коммит можно
откатить (`git revert`) или достать файл из прошлого (`git checkout <hash> -- путь/к/файлу`).
Токен и базы в git не попадают (см. `.gitignore`).
