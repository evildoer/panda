# PANDAMIA Bot 🐼

> 💬 **Говорить по-русски!** — говорят, помогает.
>
> **Это правило проекта, а не только про бота:** в комментариях к коду, строках лога, ответах в чате, README и коммитах пишем **по-русски**, когда язык это позволяет. Английскими остаются только те вещи, где иначе нельзя или не принято: имена команд и опций Discord, названия полей в API (`content`, `roles`), ключи конфига и сами идентификаторы в коде.

Discord-бот для сервера PANDAMIA: модерация голосовых каналов (права владельцев, мут/глухота, тег 🔑), бан-таймаут за выход с сервера, музыка через `/play` (YouTube и др.) и мост между серверами (pipe).

**Стек:** Node.js 24 (портативный, в папке) + discord.js v14 + keyv/sqlite + @discordjs/voice + yt-dlp.

## Запуск

Один файл на всё — **`node.cmd`** в папке бота. Двойной клик по нему (или по ярлыку на него) — бот запускается, окно = живой лог. Из консоли — то же самое:

- `node .` — привычный запуск: в папке бота команда `node` берётся из `node.cmd` (совместимая версия из папки), поэтому работает и без ярлыка;
- `node.cmd` без аргументов — тот же запуск (окно остаётся живым после остановки);
- `node script.js аргументы` — обычный запуск любого скрипта на той же версии Node;
- Node ищется сам: портативный `node-v*-win-x64` в папке бота → системный из PATH;
- **Ctrl+C → Y** — бот остановлен, окно и консоль остаются (можно `git push` и другие дела);
- `node .` в той же консоли — запустить снова; `exit` (или крестик) — закрыть окно;
- **музыка переживает перезапуск (и обновление кода):** очередь, текущий трек, место в треке и канал лежат в базе (`musicState` в `*.sqlite` рядом с ботом), поэтому после `Ctrl+C → node .` бот возвращается в тот же голосовой канал и продолжает **с того же места** (не вышло — берёт тот же трек с начала). Команды заново давать не надо. Очередь не «устаревает» и по времени, и по пустому каналу: она просто ждёт — в канале никого, значит пауза (`😴 нет слушателей`), после падения бот сам зайдёт, как только появится человек, а после `/leave` — по `/join`. Стирает очередь только `/stop` (и естественный конец очереди). Подробности и что теряется при аварийном закрытии окна — в разделе «Обновление кода и перезапуск».

Системный node должен быть ≥ 18 (для музыки ≥ 22): если старый — `node.cmd` сам возьмёт портативный из папки, а вне папки бота продолжит работать системный `node`.

**Почему в папке бота версия Node фиксирована (не убирать `node.cmd`).** В `node_modules` лежат native-модули — `@discordjs/opus` (музыка) и `sqlite3` (бан-таймауты) — собранные под конкретный ABI Node. Портативный Node в папке — это ровно та версия, под которую всё установлено, и `node.cmd` гарантирует, что `node .` возьмёт её. Любая другая версия даёт `Cannot find module '@discordjs/opus'` и музыки не будет (rest поднимется, `/play` — нет). Смена версии = переустановка зависимостей тем же Node (`npm install`); портативный Node не в git — у нового развёртывания prebuild встанет под его собственную версию.

## Настройка (первый раз)

1. Скопировать `config.example.json` → `config.json`
2. Вписать свой `ID` (application id) и `TOKEN` (Bot → Reset Token)
3. Заполнить ID сервера/каналов/ролей (ПКМ по роли/каналу → «Копировать ID», включив режим разработчика в Discord). В `config.example.json` только плейсхолдеры (`ID_СЕРВЕРА`, `ID_ПОЛЬЗОВАТЕЛЯ_1` и т.д.) -- реальных id сервера и людей в шаблоне нет
4. **После любой правки `config.json` бота надо перезапустить**: id каналов/ролей читаются один раз при старте, и старый id останется в памяти (именно поэтому перенос глухого падал с `Could not resolve channel to a guild voice channel`, когда в конфиге уже был новый канал). Битые id бот теперь проверяет при старте и пишет: `[config] channel_common = ...: канала нет -- исправь config.json и ПЕРЕЗАПУСТИ бота`
5. **Интенты.** Привилегированный **Message Content** нужен двум вещам: пересылке из `pipe_channel_source` и текстовым командам `panda ...`. В портале приложения он включён (заявку подавать не надо, пока приложение в < 100 серверах), и код его запрашивает. Если Discord его отзовёт или в `config.json` стоит `"MESSAGE_CONTENT": false` -- бот всё равно запустится, только без пересылки и без команд `panda ...` (напишет об этом в лог). **GuildMembers** бот НЕ подписывает в гейтвее (никаких событий вход/выход -- они ловятся REST-поллингом раз в 45 секунд). Но важно понимать: **полный список участников (List Guild Members) сам по себе требует этого интента на уровне приложения** -- именно им и работает поллер. То есть бот его *использует* (не подписываясь), и если Discord его отзовёт -- список перестанет приходить и вместе с ним отвалятся вход/выход: приветствие новичку, таймаут за выход и возврат ролей. Чтобы это не было незаметно: бот пишет об этом явной строкой (`[poll] список участников не пришёл (...): проверь интент Guild Members`) не чаще раза в 10 минут, а если список вдруг придёт **пустым или вразрез усохнет** -- тик пропускается, никого не записывают вышедшим и никому не выписывается таймаут (без этой защиты один сбойный ответ выглядел бы как «все вышли» и всем выписался бы таймаут, а перезаход -- бан). Из привилегий дополнительно ничего включать не нужно; у приложения уже больше 10 000 участников, поэтому Discord требует подтверждать доступ к привилегированным интентам (то самое письмо от 10.09.2026, срок -- 09.10.2026). **Без интента доступны:** один участник по id (`Get Guild Member`), поиск по префиксу и данные участника из самого слэш-взаимодействия -- на них можно переехать, если интент заберут (потеряв мгновенность вход/выход и сделав часть проверок по запросу). Из непривилегированных используется **GuildModeration** -- он даёт журнал аудита для авторства действий (`кто замутил/перенёс`)

Зависимости уже стоят (`node_modules` в комплекте). Для чистой установки: `npm install` (+ вручную докачать бинарник yt-dlp: `node node_modules/youtube-dl-exec/dist/install.js`, и `@discordjs/opus` — prebuild).

## Что умеет

- **Профильный статус бота:** виден везде, даже вне голосового. Играет музыку -- `Слушает: 🎶 Трек — «Канал» · в очереди 2 · в канале 4` (на паузе `⏸`, никого в канале -- `😴`), сидит без музыки -- `Смотрит: 🎧 «Канал» · в канале 4`, свободен -- `Играет: /help · /play · /join`. Название трека режется по лимиту поля (128 символов), а хвост с очередью и людьми остаётся. Обновлений не больше одного в 5 сек (лимит Discord на presence), текст берётся актуальный, повтор того же статуса не отправляется
- **Статус голосового канала:** пока бот сидит в канале, он пишет в его шапке, что играет (`🎶 Трек — 3:45`, на паузе `⏸`, а если никого нет -- `😴 нет слушателей: Трек`), сколько треков в очереди, сколько людей в комнате и сколько он там (`⏱ бот тут: 12 мин`). Обновляется по событиям (смена трека, очередь, вход/выход людей) и раз в минуту для счётчика времени; при выходе и при переезде в другой канал статус снимается с прежнего. Запросы к API склеиваются дебаунсом (не чаще раза в 3 сек), в лог идут только ошибки. Записи идут в Discord **по очереди** (своя очередь на канал), поэтому выход не может затереть уже отправленную строку -- в канале не остаётся устаревший статус. **Прочитать прежний статус канала Discord не даёт** (роут только пишущий, отдельного чтения нет -- проверено живым запросом: `405 Method Not Allowed`), поэтому «вернуть значение, которое было до бота» технически невозможно: вместо этого бот снимает СВОЙ статус при выходе и не переписывает чужой без изменения состояния
- **Владельцы каналов:** создав голосовой канал и получив права, участник становится владельцем: бот выдаёт ему SPEAK/MUTE/DEAF/MOVE, ставит тег 🔑 перед ником (и снимает, когда прав не остаётся; сверка догоняет теги после рестарта бота). Тег виден **сразу**, без перезахода в канал. Отдельная история (v2.15): без интента **GuildMembers** кэш ников не обновляется на смену ника, а `discord.js` при этом ещё и `fetch(id)` без `force` отдаёт **именно кэш** — поэтому свип каждые 45 секунд заново «ставил» уже стоящий 🔑 и писал ту же строку в лог (тот спам `[nick] +🔑 (sweep)`, который был виден в живом логе). Теперь ник читается из REST (`force: true`, по документации Discord этот одиночный запрос привилегированного интента не требует), а состояние читается свежим ТОЛЬКО когда оно неизвестно или расходится с правами: что бот поставил сам, он помнит в памяти процесса (`$nickSet`). Проверено стендом: первый свип ставит ключ одной строкой, второй и третий — молчат и в REST не ходят; Роли ADM/MOD (`role_admin`/`role_moder`) -- исключение: ключа у них не бывает (права есть всегда и все свои это знают), самодорисованный бот удаляет
- **Мут/глухота:** мут в чужом канале → оверрайд SPEAK:false + ЛС-уведомление + журнал; глухота в чужом канале → CONNECT:false + перенос в общий канал. **Общий канал `channel_common` -- это канал жалоб:** заходя туда, человек сразу размучивается и раздефливается (`get appeal in ...` + запись 🆘 в журнал), чтобы мог сказать, за что его наказали. Пер-канальные запреты при этом остаются на своих каналах и возвращаются, как только он туда зайдёт («мут помнится по каналу»). Раньше эта ветка (в коде — `unMUTE for Appeal!`) была недостижима из-за раннего `return`: замученный заходил в общий канал и оставался замученным. Следствие: мут/глухота, выданные уже **внутри** общего канала, там же и снимаются (это и есть «жалоба»), а в остальных каналах наказания работают как раньше
- **Приветствие новичку (вернулось):** при входе на сервер бот пишет в личку приветствие, в котором **сам текст и картинка из сообщения с правилами** (`welcome_message` в канале `welcome_channel`), плюс ссылка на это сообщение (v2.17). Раньше в письме была **только ссылка**, и Discord рисовал её как название сервера -- выглядело так, будто текст потерялся. Нужны **оба** ключа, и это не прихоть: в Discord **нет способа найти сообщение по id без канала** (поиск есть только по тексту внутри канала), поэтому `welcome_channel` -- «где искать», `welcome_message` -- «что именно». Нет id сообщения -- в письме будет ссылка на канал; нет `welcome_channel` -- приветствие выключено целиком; сообщение не отдалось (удалили, нет прав) -- письмо уйдёт со ссылкой, как раньше, и в логе будет причина. В логе видно само событие и что попало в письмо: `[welcome] ЛС новичку <ник> отправлена (https://...) -- текст и картинки взяты из сообщения с правилами`; закрытая личка не ошибка бота -- в лог идёт причина. Перезаходы в таймауте приветствия не получают (у них другой путь -- бан-таймаут), а обычный возврат на сервер -- получает (бот не различает «новичок» и «вернулся»: истории входов у него нет, и с интентом Guild Members тоже -- он даёт только события, а не историю). **Задержка (v2.17):** с интентом Guild Members вход приходит мгновенно, без него -- опросом раз в 45 секунд (тогда письмо может прийти до минуты после входа; в журнале событие видно сразу). **Свой текст к правилам -- по желанию (v2.18, `welcome_prefix`):** по умолчанию (`true`) к тексту и картинкам из сообщения с правилами бот добавляет своё приветствие и краткое описание возможностей (`/play`, `/queue`, `/help`); `"welcome_prefix": false` -- в ЛС уходит ТОЛЬКО сообщение с правилами и ссылка на него, без описания бота. **Проверить глазами (v2.18):** слэш-команда `/welcome` -- бот пришлёт тебе ту самую ЛС (`/welcome user:@кто` -- другому, staff); в чате то же делает `panda welcome`, но она зависит от интента Message Content и после его отзыва перестанет работать, а `/welcome` -- нет.
- **Бан-таймаут:** выход с сервера → таймаут 20 мин (настраивается `onLeaveBanTimeout`); перезаход в течение таймаута → ЛС-предупреждение + бан до конца срока; при `onLeaveBanRealy: true` бан выдаётся сразу при выходе, при `false` -- только при перезаходе. **В логе и в ЛС -- ровно то, что сделано:** `timeout on 20 min. (ban -- only if re-enters earlier)` и `timeout expired after 20 min. (did not come back)` против `banned on 20 min. (on leave)` / `banned on ~N min. (re-enter during timeout, left 0:03:20)` у настоящих банов. Письмо «вам ограничен вход» перезаходящему уходит только когда бан действительно будет выдан (при `onEnterBanRealy: false` вместо письма в лог идёт `came back during timeout, but no ban`), а запись таймаута с уже прошедшим сроком считается обычным входом (человек получает приветствие, а не письмо с прошедшей датой). Запись из базы снимается только ПОСЛЕ того, как бан реально снят: если снятие не удалось (права/сеть), бот помнит и повторит в следующем тике, а не потеряет человека в бане. Разбан автоматический, переживает рестарт бота (SQLite: время конца таймаута лежит в базе, `setTimeout` в памяти -- только чтобы снять вовремя). **Снять наказание вручную** — `/unban user:@кто reason:...` (админы/модеры): бот снимает и бан в Discord, и запись таймаута, и отложенный таймер разбана; кто снял и почему — в журнал, в лог (`[ban] <кто> снял наказание с <кого> (таймаут, срок был до ..., причина: ...)`) и в историю. Если бан снять не удалось (права/сеть) — бот НЕ чистит запись и не пишет ложной записи в журнал, а честно отвечает причиной
- **Без паузы между треками:** пока играет текущий, поток следующего уже готовится (`предзагрузка готова: ...`), поэтому следующая песня стартует сразу (`предзагрузка сыграла: ... (без паузы)`), а не после поиска и буферизации. Непригодившаяся заготовка глушится вместе с yt-dlp (при `/stop`, очистке очереди и выходе из канала) -- лишних процессов не остаётся. Если заготовка сломалась (видео удалили, сеть), трек просто берётся заново обычным путём
- **Бот НИЧЕГО не забывает (очередь, текущий трек, место в треке, канал):** всё лежит в базе (SQLite), сохраняется на каждом изменении, раз в 20 сек и **в момент Ctrl+C**. Отдельная важная правка: в keyv v5 строка-URI больше не подгружает адаптер — `new Keyv('sqlite://...')` молча уходил в память, и база на диск не писалась вообще (баны не переживали перезапуск). Теперь адаптер передаётся явно (`@keyv/sqlite`), ошибки базы видны в логе строкой `[db] ...`. Очередь не «устаревает» по времени: после перезапуска, падения или `/leave` бот помнит её сколько угодно. **Забывает её только `/stop`** -- и ещё естественный конец очереди (когда она доиграла до конца живым слушателям: `[music] очередь доиграна до конца`). Восстановление: после падения бот сам заходит в тот же канал, **как только там появится живой слушатель** (`очередь ждёт слушателя`); после `/leave` сам не лезет -- ждёт `/join` (`очередь с прошлого раза на месте (выходили по /leave) -- ... ; продолжу по /join`). Продолжает с того же места (`возобновляю очередь в «Канал»: Трек (с 1:24) + ещё 3 в очереди`), сдвиг запрашивается даже с 1 секунды и даже если до конца оставалось 15 сек; если сдвиг не сработал (источник не умеет), берёт тот же трек с начала (`продолжение с 01:24 не удалось -- беру трек с начала`)
- **Обрыв связи/потока не бросает трек:** если yt-dlp отвалился посреди песни, бот возвращает трек в очередь и продолжает его **с места обрыва** (`поток оборвался (на 00:42, ...) -- продолжаю тот же трек, попытка 1/3`), а не перескакивает дальше. Три попытки подряд -- тогда пропускает и пишет в канал `⚠️ ... пропускаю` (чтобы не биться в мёртвый источник бесконечно). Обрыв голосового соединения (`Disconnected`) тоже не теряет очередь: `[music] вышел из «Канал» (очередь сохранена, обрыв связи: Трек ждёт, 3 далее)`, и бот вернётся сам, когда в канале будет кто-то живой
- **Музыка не играет в пустоту:** если в канале не осталось **живых слушателей** (боты и сам бот не считаются), трек ставится на паузу (`в «Канал» никого -- пауза`), в статусе и профиле -- `😴 нет слушателей: Трек`. Как только кто-то зашёл -- продолжает с того же места (`слушатель вернулся в «Канал» -- продолжаю`). Ручная `/pause` при этом не ломается: уход и возврат слушателей её не отменяют
- **Кто первый -- тот и прав:** `/play` добавляет трек в конец очереди. Если бот уже играет живым слушателям в другом канале – не переезжает, DJ просто пополняет очередь (`🎧 Играю в «...» -- там и продолжу`); если бот сидит один -- переезжает к тому, кто позвал. **`/join` тоже больше не перехватывает бота силой (v2.18):** если бот играет трек и его **автор сидит в той же комнате** (то есть бот поёт именно для него), другой DJ команду получает с отказом (`🎧 Не перееду: я играю **Трек** в «...» для автора трека (Лахуля)`) -- увести можно только честно: `/skip`, `/stop`, когда автор сам уйдёт или когда дойдёт до трека другого автора. Если автора в комнате нет -- `/join` работает, а если при этом в старой комнате оставались живые слушатели, бот прямо об этом напишет (`🎧 В «...» оставались слушатели -- теперь они без музыки`) и оставит строку в логе: DJ видит последствие своих действий. Правило одно для всех, у кого есть права DJ/админ/модер, и в логе видно автора: `[music] (кто: DJ) /join отклонён: играю для автора трека Лахуля в «Комната¹»`. **Стоять в голосовом канале не обязательно:** DJ может набирать плейлист откуда угодно, бот заиграет по `/join` (пока пишет `⏳ Я не в канале -- заиграю, когда позовёшь /join`). Позвал `/join` в канал, где нет музыки -- подберёт очередь и продолжит с места
- **Бот играет там, где слушает автор трека (v2.18):** тот, кто добавил трек, ставит его для себя -- поэтому если автор трека сидит в голосовом канале, в момент старта этого трека бот **переезжает к нему** и остаётся там до трека другого автора (или до `/leave`), а если до трека того же автора дошло ещё раз -- он уже там. Автора в голосовом нет -- бот не двигается; сам он по-прежнему **никогда** не заходит и не выходит: переезд возможен только когда он уже где-то играет. Сразу после явного `/join`/`/play` (5 секунд) бот тоже не уезжает -- иначе он уехал бы от того, кто его только что позвал. Причина видна в логе: `[music] перешёл в «Канал²» -- автор трека Лахуля слушает здесь`, а выбранный канал запоминается (`savedChannelId`), поэтому после перезапуска бот продолжает там же. Тот же смысл и у паузы: если бот стоит **один** (в комнате никого -- `😴`), а автор музыки зашёл в другую комнату, бот переезжает к нему и продолжает с того же места (`здесь никого, а автор трека ... слушает здесь`) -- кто поставил трек, тот его и слушает. Приоритет -- у автора **недоигранного** трека (он сейчас и играет), а если тот уже ушёл -- у автора **следующего** в очереди: иначе пауза запирала бы бота в пустой комнате и трек следующего автора не начался бы никогда. Переезд делается один раз на событие (бот не бегает между двумя авторами туда-сюда), а если в комнате есть хоть один живой человек -- бот никуда не двигается вообще. Это и есть ответ на «тащить бота руками»: тот же путь работает для **Stage-каналов (сцена)** -- бот туда заходит, но Discord не даёт ему вещать, пока он не спикер, поэтому в лог идёт подсказка `«Сцена» -- Stage-канал: чтобы музыку было слышно, Stage Moderator должен сделать бота спикером`
- **Объявление и ЛС без интента Message Content (v2.18):** `/announce text:... file:... channel:...` (staff) публикует объявление **от имени бота** (по умолчанию -- в тот канал, где вызвали), `/dm user:@кто text:...` (только админы) отправляет человеку личное сообщение, а **правый клик по сообщению -> «Переслать в общий»** (staff) пересылает чужое сообщение в общий канал -- с текстом и вложением. Всё это берёт данные из самой команды, поэтому интент Message Content им **не нужен** (Discord сам советует такой путь в гайде «You Might Not Need a Privileged Intent»), и это работающий запасной вариант, если интент отзовут: заявка на него в этом смысле больше не критична. У «Переслать в общий» есть важная осторожность: оригинал удаляется **только в канале-источнике** моста (`pipe_channel_source`) -- если staff переслал сообщение откуда-то ещё, оно остаётся на месте (удалять чужое сообщение по одному клику нельзя), и в ответе это сказано прямо. Отправка у меню и у старого моста -- **одна и та же функция** (`relayPipe`), так что порядок «сперва отправка, потом удаление» и передача вложений ссылкой одинаковы. В логе видно авторство: `[pipe] (кто: Admin) переслал сообщение Лахуля -> #общий + вложение: ... (оригинал удалён)`
- **Что бот помнит о человеке -- `/rolecheck user:@кто` (v2.17, админы/модеры):** отчёт по одному человеку: есть ли он сейчас на сервере и какие роли у него сейчас; что лежит в памяти о его ролях (`save_roles`: дата записи, полный список, что именно **вернётся при входе**, что вычеркнуто и почему -- «уже есть» / «исключена в config» / «роли больше нет на сервере», и предупреждение, если запись старше `save_roles_days`); текущее наказание с точным сроком и причиной; история за окно (`выходов 2, таймаутов 1, банов 1, снятий 1`). Команда работает **и для того, кто не на сервере**: всё лежит в базе по id, а для проверки самого человека хватает одиночного REST-запроса («Get Guild Member»), которому интент Guild Members не нужен. В лог пишется факт вызова (`[roles] /rolecheck: <ник> -- отчёт выдан`)
- **Управление очередью:** `/queue` (с номерами), `/remove number` (убрать трек), `/move number to` (переставить на другое место), `/jump number` (сразу к треку, всё перед ним выбрасывается), `/clear` (очистить очередь, текущий трек доиграет), `/clear author:@кто` (убрать из очереди ТОЛЬКО треки этого человека -- длинные плейлисты собирают несколько DJ, а убрать надо одного). Номера в `/queue`, `/remove`, `/move` и `/jump` -- одни и те же (текущий трек в нумерацию не входит -- он показан строкой «Сейчас»), права -- как у музыки (DJ). Перестановка учитывает предзагрузку (заготовка переезжает на новый первый трек) и не трогает играющую песню; если двигают трек, ждущий продолжения после `/leave`/обрыва, место в нём едет вместе с треком, а его позиция в очереди запоминается (`curIdx`), поэтому после перезапуска порядок не откатывается
- **Очередь: страница до 25 треков и перестановка кнопками (v2.17–v2.18):** на странице `/queue` теперь **до 25 треков** (было 10 -- в очередь часто заливают по 50, меньше листать), а `from:26` открывает нужную страницу. Бюджет страницы считается от **реального текста** шапки, «до конца очереди» и подсказки, поэтому место используется до конца лимита Discord (~2000 символов): раньше стоял жёсткий бюджет и страница обрезалась до 22 треков. Если у трека длинное название -- строк на странице будет меньше, но обрезки списка «между страницами» нет: «◀ Назад / Вперёд ▶» ведут ровно по показанным номерам. Ещё один источник места: **автор у идущих подряд треков одного человека пишется один раз** (`· 👤 ник` в первой строке, дальше -- молча), поэтому плейлист одного DJ помещается целиком, а смена автора всегда видна. Под очередью, кроме «🗑 Убрать трек», есть меню **«🎚 Двигать трек»**: выбрал трек -- рядом появились **«⬆ Выше» / «⬇ Ниже»** (и «✖ Готово»), двигать можно сколько угодно раз подряд, номер всё время виден в списке; обычная кнопка -- без `/move` по номерам. Логика перестановки -- одна и та же с `/move` (общая функция), так что ответы и запись в лог не разъезжаются: `[music] (кто: Admin) переставил в очереди №3 -> №1: ...`. Права -- как у музыки (DJ/админ/модер)
- **Очередь глазами DJ (v2.14):** в `/queue` видно **автора каждого трека** (`· 👤 ник`) -- у длинных очередей видно, кто что поставил (автор запоминается вместе с треком и переживает перезапуск), **сколько уже играет текущий трек** (`00:40 / 02:00`) и **сколько всего ждать до конца плейлиста** (`⏳ До конца очереди: 1 ч 12 мин`), причём остаток считается точно -- с учётом позиции в текущем треке; эфиры (🔴, у них длительности нет) и треки без длины считаются отдельно, чтобы цифра не врала. У очередей, которые не влезли в страницу, появляются **кнопки листания «◀ Назад / Вперёд ▶»** (в customId -- целевая страница, содержимое берётся из живой очереди; перлистывать может только тот, кто вызвал `/queue`), а `/queue from:N` работает как и раньше (страница -- до 25 треков)
- **Роли между перезаходами (v2.14, `save_roles`, по умолчанию ВКЛЮЧЕНО):** выходя с сервера, человек больше не теряет роли -- бот запоминает их (ключ -- id участника) и при возврате **добавляет недостающие**. Раньше это умел только сторонний бот; теперь это делает сама PANDAMIA, и **одновременно с другим ботом-хранителем ролей**: бот только добавляет и никогда ничего не снимает (у кого роль уже есть -- не трогает), так что «кто первый успел, тот и вернул», и права гарантированно на месте. В базу не попадают @everyone, роли интеграций (managed) и уже удалённые роли; свой список исключений -- `save_roles_exclude`, срок хранения -- `save_roles_days` (**по умолчанию НАВСЕГДА: `0`**; задано число -- записи старше него убирает свип). Выключить: `"save_roles": false` у сервера. **Точность (v2.16):** роли хранятся не «как бог на душу положит», а ровно на момент выхода -- снимок поллера бывает до 45 секунд старым, поэтому правки ролей, случившиеся после снимка, достраиваются по журналу аудита: роль, снятая за секунды до выхода, в базу НЕ попадёт и не вернётся при входе, а выданная за секунды до выхода -- попадёт. Если возвращать нечего -- старая запись стирается (иначе она воскресила бы уже потерянную роль). Рядом живёт аналогичная настройка истории наказаний: `bans_history_days` (**по умолчанию тоже НАВСЕГДА: `0`**) — окно сводки в `/bans`: за годы видно, кто перезаходит и сколько раз был наказан; задано число -- старые события убирает свип
- **Видно, кто в наказании и кто как наказывался (v2.14–v2.15):** `/bans` (только админы/модеры, ответ виден вызвавшему) показывает всех, у кого действует таймаут/бан: имя, что это (🚫 бан или ⏳ таймаут -- проверяется по списку банов Discord), точный срок снятия (`снимется 18.09.2026, 21:04:33 (через 00:03:20)`) и причину из аудита. Ниже — **сводка** за окно `bans_history_days` (по умолчанию -- **за всё время**, `0`; задано число дней -- «за N дн»): `• **Кто** -- выходов 3, таймаутов 2, банов 1, снято 1 _(последнее: 18.09.2026, 21:04:33)_`. События пишутся сразу, как происходят (выход, таймаут, бан, снятие — в том числе вручную через `/unban`), окно истории настраивается, а при хранении «навсегда» свип историю не трогает вообще. Снять наказание досрочно — `/unban`. Вызов любой команды, как и все остальные, попадает в лог
- **Громкость песен не «прыгает» (v2.14, `MUSIC.normalize`, включено):** записи сведены с разной громкостью, поэтому раньше одну песню хотелось пригромче, другую потише. Теперь между yt-dlp и Discord стоит свой ffmpeg с фильтром `loudnorm` (`MUSIC.filter`), который приводит песни к одному среднему уровню -- команды и настройки не нужны. Фильтр проверяется один раз при старте (в логе: `выравнивание громкости: включено -- loudnorm=...`); если сборка ffmpeg его не умеет или в конфиге `normalize: false` -- играем как раньше, музыка из-за этого не встаёт
- **Процессы за собой убираются (v2.14, важный фикс):** `player.stop()` в @discordjs/voice НЕ закрывает поток трека, поэтому после каждого `/skip`, `/stop` и `/leave` процессы yt-dlp и ffmpeg оставались висеть в памяти. Теперь у играющего трека есть ссылка на его поток, и он глушится при любом конце трека (доиграл, пропустили, остановили, вышли) -- лишних процессов не остаётся
- **Бота можно тащить руками (v2.14):** если админ перетащит бота из комнаты в комнату, это видно в логе (`[music] бота перенесли: «Канал¹» -> «Канал²»`), статус с прежнего канала снимается, а пауза/продолжение работают по обычному правилу слушателей: в новой комнате никого -- пауза (`😴`), зашёл человек -- продолжает с того же места
- **Прямые эфиры:** `/play` со ссылкой на трансляцию работает и помечается отдельно -- 🔴 в статусе канала и профиле, `Длина: 🔴 LIVE` в ответе и очереди (у эфира длительности нет). У обычного трека, для которого YouTube не отдал длину, теперь `--:--`, а не «LIVE» -- раньше эти два случая не отличались. Перезапуск эфир не перематывает (перематывать там нечего) и теряет только те секунды, что бот не работал
- **Музыка:** `/play` (ссылка/поиск/плейлист/эфир -- добавляется в конец очереди), `/join` (зайти в канал и остаться там, музыка не нужна -- удобно «посидеть с ботом»; если у бота есть сохранённая очередь, продолжит её), `/skip`, `/stop` (стоп + забыть очередь), `/pause`, `/resume`, `/queue`, `/leave` (выйти, очередь и место помнит), `/remove number`, `/move number to`, `/clear`, `/jump number` (плюс `/help`). Под ответом `/queue` -- быстрые кнопки: «⏭ Пропустить», «🧹 Очистить», меню «🗑 Убрать трек» и «🎚 Двигать трек» (со «⬆ Выше» / «⬇ Ниже») с номерами текущей страницы (те же номера, что в `/remove`); жмёт тот, у кого права DJ, а листать может только тот, кто очередь открыл. В логе видно авторство: `[music] (кто: Admin) убрал из очереди №3: ...`. Сам бот не уходит: кончилась песня или `/stop` -- он остаётся в канале, пока не позовёшь в другую комнату или не скажешь `/leave` (заход и выход видны в логе: `[music] подключился к ...` / `[music] вышел из ...`). Права: админ, модер или роль DJ (`role_dj`). YouTube ходит через прокси `MUSIC_PROXY` (socks5), если прокси не отвечает 3 секунды — напрямую (DIRECT)
- **Мост серверов (pipe):** сообщение человека в `pipe_channel_source` (пандалогия) пересылается в `pipe_channel_target` (общий чат) **от имени бота**, затем оригинал удаляется. Пересылается и текст, и **вложения** (картинки/файлы): раньше объекты вложений передавались в Discord как есть и терялись, из-за чего на сообщение-картинку бот отвечал `50006 Cannot send an empty message` -- теперь вложения передаются ссылкой, а файл без текста пересылается как файл. Порядок именно такой (сперва отправка, потом удаление) -- при ошибке отправки сообщение остаётся в источнике, а не пропадает. Требует интента **Message Content**: без него Discord присылает событие с пустым текстом, и бот ничего не пересылает и ничего не удаляет (в логе: `[pipe] ... НЕ переслано`). Один источник текста на все три входа — `/help`, `panda help` и стартовая ЛС. В тексте есть всё новое: `/bans`, чистка очереди по автору, кнопки листания и контакты владельцев

- **Команды в чате:** `panda ping`, `panda help`, `panda file`, `panda test`, `panda welcome [@юзер]` (посмотреть приветствие новичка -- в v2.18 у этого появился слэш-близнец `/welcome`, работающий без интента Message Content), `panda dm @user текст` (админам; теперь то же самое удобнее слэш-командой `/dm`, которая НЕ требует интента Message Content, -- текстовая команда осталась как привычный путь). `panda dm` принимает и упоминание, и просто id (`panda dm 123456789012345678 текст`); команду бот удаляет **только после успешной отправки**, а если ЛС не ушло -- пишет причину в канал и в лог (раньше в этом случае была полная тишина, а команда всё равно удалялась). `panda test` -- самопроверка: бот пишет ЛС тому, кто её вызвал (никаких зашитых id в коде нет)
- **Что бот поднял из базы (v2.14):** при каждом старте в лог идёт строка про баны/таймауты, причём всегда -- даже когда наказаний нет: `[ban] из базы поднято 0: активных банов/таймаутов нет -- никто не наказан` или `[ban] из базы поднято 2 активных (1 бан, 1 таймаут): Должник до 18.09.2026, 21:04:33 (осталось 00:03:20, бан) | ...; просроченных записей: 1 -- сниму сейчас`. Это ровно то, что нужно после перезапуска: видно, не наказал ли кого бот за время, пока он не работал (раньше это приходилось выяснять только по журналу Discord). Сроки везде точные, до секунды
- **Что значит «убрал N записей» в логе (v2.17):** это про **срок хранения**, а не про потерю данных. Свип (раз в 45 сек и при старте) удаляет из базы то, что старше окна, и пишет это явно: `[ban] истёк срок хранения истории 30 дн (bans_history_days): удалено из базы 2 записи -- событий в них уже не было, активные наказания не тронуты` и `[roles] истёк срок хранения 30 дн (save_roles_days): удалено из базы 1 запись о ролях -- эти роли всё равно не вернулись бы (запись просрочена)`. **По умолчанию удалять нечего (v2.18):** оба ключа -- `0` = хранить всегда, и тогда этих строк в логе не бывает (а записи без даты, оставшиеся от старых версий, убираются всегда -- по ним всё равно нечего вернуть). Активные таймауты, баны и свежие записи о ролях не трогаются: окно настраивается (`bans_history_days`, `save_roles_days`)
- **При старте** бот шлёт ЛС с инструкцией списку людей из `STARTUP_DM`. Контакты в тексте помощи настраиваются: `OWNER` (верхний ключ) -- владелец **хостинга** бота, тот, кто его запускает; `owner_server` (у сервера) -- владелец **сервера**. Это разные люди, и каждый показывается своим флагом (`show_owner_hoster` / `show_owner_server`); если ничего не указано, в помощи останется «администрации сервера». Так в коде нет ни одного зашитого id, и репозиторий можно отдавать людям
- **Проверить приветствие на себе (v2.18):** `/welcome` -- бот пришлёт в ЛС ровно то приветствие, которое видят новички (удобно править `welcome_message` и сразу смотреть результат, кэш не мешает); `/welcome user:@кто` -- то же на конкретном человеке (доступно staff). В чате осталось и привычное `panda welcome [@юзер]`, но она держится на интенте Message Content, а `/welcome` работает без него. Событие попадает в лог: `[welcome] проверка: <кто> -> <кому> -- с текстом и картинкой из сообщения с правилами`
- **Удалить сохранённое о человеке -- `/forget user:@кто` (v2.18, staff):** бот убирает из своей базы всё, что накопил по этому человеку: роли для возврата (`memberRoles`) и историю наказаний (`banHistory`), а в ответе пишет, что именно удалил (или что удалять было нечего). **Активное наказание при этом не трогается** -- оно снимается `/unban` (это действие модерации, а не «хранение данных»), и в ответе об этом сказано прямо. Стоит в одном ряду с «не хранить лишнего»: данные и так лежат только локально в `*.sqlite` и не уходят никуда, а команда закрывает вопрос «как человеку запросить удаление своих данных» -- он есть в заявке на привилегированные интенты
- **Лог (окно бота) -- только события**, без периодического шума: вход/выход/переход по голосовым каналам, микрофон/наушники/стрим/камера, создание и удаление каналов, музыка (`[music] играю: ...`), слэш-команды и `panda ...` (`[cmd]`). Если в конфиге битый id -- при старте будет строка `[config] ...`; если не удался перенос глухого участника -- `[voice] перенос ...`. Остальное молчит. Повторов одного и того же в логе нет: свип ключей 🔑 больше не переписывает ту же строку каждые 45 секунд (v2.15) — строка `[nick] +🔑` появляется только когда тег **реально** изменился, и тогда же делается один запрос к API. Каждая строка -- одна строка: ошибки yt-dlp пишутся одной строкой с причиной из его же stderr (`[music] yt-dlp exited: ERROR: [youtube] ...: Video unavailable`), без команды и многострочной простыни. У запуска трека тоже одна строка: `[music] играю: Название (из предзагрузки, без паузы)` -- раньше рядом появлялась отдельная `предзагрузка сыграла: ...`, которую по логу читали как «прошлый ролик отыграл» (v2.14). Если процесс ffmpeg выравнивания громкости умрёт на середине, будет одна строка с причиной, без падения бота. У мутов/глухоты/переносов указывается ещё и **автор** (`кто: ...`): Discord не присылает его в голосовых событиях, поэтому он берётся из журнала аудита (интент **GuildModeration** -- НЕ привилегированный, одобрения не требует; нужен право «Просматривать журнал аудита», при приглашении с `permissions=8` оно есть).

## Интенты: что доступно сейчас и что будет 9 октября 2026

Бот старается жить на непривилегированных интентах, но две вещи без них не сделать: **Message Content** (текст сообщений -- команды `panda ...` и мост из пандалогии) и **Guild Members** (события входа/выхода и полный список участников, из которых растут приветствие новичку, таймаут за выход и возврат ролей).

Важное открытие (v2.17): **полный список участников по REST -- это ровно та возможность, которую даёт Guild Members**. То есть «работа без интента» последние версии была только на бумаге: список приходил потому, что приложение этим интентом уже владеет. Поэтому интент теперь запрашивается явно (`"GUILD_MEMBERS": true`), вход/выход ловятся мгновенными событиями, а опрос раз в 45 секунд остался **резервным** путём (бот был выключен -- переходы добираются опросом; интента нет -- работает только он, и в логе будет строка об откате). Один и тот же переход не обрабатывается дважды: отметка «уже разобрано событием» живёт 5 минут, иначе только что вошедший в следующем тике выглядел бы как вышедший и получил таймаут.

При каждом старте в лог идёт отчёт **по факту**, а не по настройке:

```
[intents] 🐼PANDAMIA🐼 | Message Content (текст сообщений, команды "panda ..."): да
[intents] 🐼PANDAMIA🐼 | Guild Members (мгновенные вход/выход): да
[intents] 🐼PANDAMIA🐼 | полный список участников (REST): да -- 11608 участников (от него зависят вход/выход, таймаут за выход и возврат ролей)
[intents] 🐼PANDAMIA🐼 | журнал аудита (авторство мутов/переносов): да
```

Плюс одна строка про **все** серверы сразу (включая те, где бот есть, а в `config.json` его нет): `[login] приложение в 2 серверах, участников суммарно ~11745 (🐼PANDAMIA🐼 ~11608 | Старый ~137)`. Число людей приходит вместе с каждым сервером (`memberCount` в событии GUILD_CREATE), поэтому «сколько нас всего» видно прямо в логе -- без похода в портал и без интентов.

Про 9 октября 2026 (письмо от 10.09.2026, срок продлён до этой даты): по документации Discord порог считается **не по числу серверов, а по числу уникальных пользователей, которые могут видеть приложение**. На одном твоём сервере 11 608 участников -- порог в 10 000 уже превышен, поэтому привилегированные интенты нужно подтверждать **запросом в Developer Portal**; без одобрения 9 октября их заберут. Это не ломает запуск: бот стартует без интента (в логе `[login] Discord запретил интент ... -- переподключаюсь без него`), но теряется ровно то, что на них держится:

| Возможность | Без Guild Members | Без Message Content |
|---|---|---|
| Вход/выход: приветствие новичку, таймаут за выход, возврат ролей | **нет** (нет ни событий, ни списка) | есть |
| `panda ...` в чате, мост из пандалогии (pipe) | есть | **нет**, но есть `/announce` и «Переслать в общий» |
| Музыка, мут/глухота, ключи 🔑, статусы, `/bans`, `/rolecheck` | есть | есть |

### Как устроено ревью (по документации Discord от 10.06.2026)

- Порог считается **по уникальным пользователям, которые видят приложение** (не по числу серверов). Уведомление даётся, когда порог 10 000 превышен **и** какой-то привилегированный интент включён или его пытаются включить -- как раз наш случай.
- На подачу заявки -- **90 дней** с даты уведомления (в письме от 10.09.2026 срок продлён до **9 октября 2026**). Пока заявка на рассмотрении, приложение **работает как обычно и может входить на новые серверы**. Заявку можно подать и позже -- доступ просто потеряется до одобрения.
- **Проверка личности владельца для этого не требуется:** ревью смотрит на назначение бота, а не на паспорт. Отдельная верификация с документами -- это другой процесс (для приложений, которые хотят стоять в 100+ серверах).
- Что смотрит ревью: конкретное назначение; просьба **только нужных** интентов (Presence нам не нужен, и мы это подчёркиваем); как бот обходится с данными (что в памяти, что хранится и сколько). Готовый текст заявки -- `intents-request.md`, в репозиторий он **не попадает** (там id реального сервера, файл в `.gitignore`).
- Про приветствия в гайде Discord сказано буквально: «Мои приветственные сообщения перестали работать» -> **Fix: Enable and request the Guild Members intent** -- то есть это один из признанных поводов для интента, а не «на всякий случай».

### План Б: что делать, если интенты всё-таки заберут

Заявка -- путь A. Путь B (жить без интентов) выглядит так, и он у нас частично уже готов:

| Что теряется | Почему нельзя без интента | Что можно сделать |
|---|---|---|
| Мост из пандалогии, команды `panda ...` | Discord присылает события с пустым `content` | **Сделано:** `/announce`, `/dm` и «Переслать в общий» (правый клик) -- всё из самой команды |
| Приветствие новичку в ЛС | Нет ни `GUILD_MEMBER_ADD`, ни списка участников | Автоматически -- никак (Discord прямо советует для этого интент). Остаётся `panda welcome` для проверки текста и указатель на `/help` в правилах |
| Таймаут за выход | Нет событий входа/выхода | **На частичных данных:** member-объект приходит в **голосовых событиях и взаимодействиях** (это НЕ привилегированные интенты), а в нём есть `joined_at` и список ролей. Значит можно вести память «когда я последний раз видел человека и какие роли у него были» и ловить перезаход по изменившемуся `joined_at` -- наказание догонит человека при первом же его действии (зашёл в голос или вызвал команду), а не мгновенно |
| Возврат ролей | Списка участников нет | Одиночный запрос «Get Guild Member» **без интента работает** (раздел «You Might Not Need a Privileged Intent»); роли можно запоминать в момент **любого** наблюдения человека (голос/команда) и возвращать при следующем наблюдении |
| Общий счёт "кто-то вышел" | Списка нет | `approximate_member_count` из обычного `GET /guilds/<id>?with_counts=true` -- это не интент: видно, что число упало, а вот **кто** -- только по частичным данным выше |

Практический вывод: если вход/выход и возврат ролей нужны -- имеет смысл подать запрос в Developer Portal (форма Privileged Intents) и описать назначение (модерация голосовых каналов, возврат ролей). В коде предусмотрено оба варианта: любой интент можно выключить в `config.json` (`"GUILD_MEMBERS": false`, `"MESSAGE_CONTENT": false`) -- бот отработает без ошибок и честно скажет об этом в логе.

## Комментарии в конфиге

В JSON комментариев не бывает, поэтому подсказки лежат **обычными ключами с окончанием `_comment`** (идея владельца): код их не читает, JSON остаётся валидным, а понять, что куда вписать, можно прямо в файле.

```json
"log_channel_comment": "Текстовый канал-журнал: вход/выход, мут/глухота, музыка.",
"log_channel": "804684593684152330",
"onLeaveBanRealy_comment": "false -- при выходе бан не выдаётся, только запоминается срок.",
"onLeaveBanRealy": false
```

Важная деталь: **внутри `SERVERS` ключ -- это id сервера**, поэтому подсказки внутри блока называются так же (`"470047648112705546_comment"`), а бот при загрузке выкидывает всё, что не похоже на id (и молчит про `_comment`). Если в `SERVERS` попадёт странный ключ, в логе появится строка `[config] ключ "..." в SERVERS -- не похож на id сервера -- пропускаю его`. Верхний ключ `_ПРО_КОММЕНТАРИИ` -- тоже просто подсказка. **Заготовка из `config.example.json`** (`"ID_СЕРВЕРА"`) распознаётся ОТДЕЛЬНО -- это не ошибка того, кто только что скопировал шаблон: вместо «странного ключа» бот пишет `[config] в SERVERS осталась заготовка (ID_СЕРВЕРА) -- вместо неё впиши id своего сервера`, а если рабочих серверов не осталось -- честно говорит, что запустится, но делать ничего не будет.

## Настройка: исторические ключи

В `config.json` могут остаться ключи от старых версий -- код их не читает, можно удалить. Уже удалены как мёртвые: `admins` (админов определяют роли `role_admin`/`role_moder`), `log_channel_temp` (второй журнал), `afkLikeChannels`, `logo`. Роли `role_for_*` **живые** -- их читает код (они выдаются владельцам каналов), а вот `role_for_manage` нужен только в личных каналах.

## Обновление кода и перезапуск

Что проверено на живом стенде (и почему состояние не теряется):

- **очередь, текущий трек, место в треке и канал живут в `*.sqlite` в папке бота**, а путь к базе строится от `__dirname` (папка модуля), а не от текущей папки. Значит любой способ запуска -- ярлык, `node .`, `node.cmd` из другой рабочей папки -- пишет и читает **одну и ту же** базу; APP-режим `node.cmd` ещё и сам делает `pushd "%~dp0"`, так что «Рабочая папка» в ярлыке может быть любой;
- **обновление кода (`git pull`, переключение веток, правка `index.js`)** базу не трогает: `*.sqlite` в `.gitignore`. После перезапуска бот поднимает очередь из неё же (`возобновляю очередь в «Канал»: Трек (с 1:24) + ещё 3 в очереди`);
- **`Ctrl+C`** сохраняет сразу (`сохраняю очередь перед выходом...`, не дольше 1.5 с) -- очередь и секунды позиции уходят в базу. Дальше cmd.exe спрашивает `Завершить выполнение пакетного файла [Y/N]` -- это вопрос **оболочки**, а не бота: бот в этот момент уже сохранился и вышел;
- **пока играет трек**, позиция дописывается каждые **5 секунд** (у позиции нет событий -- только таймер), а очередь и все переходы (`/play`, `/stop`, `/leave`, смена трека) -- сразу по событию;
- **при закрытии окна крестиком** Windows убивает процесс без сигнала, поэтому последние секунды позиции могут потеряться (очередь и трек к этому моменту уже в базе) -- максимум 5 секунд. Хочешь точнее -- `Ctrl+C`;
- **не запускать `git clean -xfd`** в папке бота: он сотрёт всё, что в `.gitignore`, то есть **базу с очередью и портативный Node** (`node-v*`). Чистая копия без последствий -- это `git stash`/`git checkout` или просто `git pull`;
- **смена версии Node = переустановка зависимостей** (`npm install` тем же Node): от ABI зависят `@discordjs/opus` (музыка) и `sqlite3` (вся база). Старый Node (например через `nvm use 16`) даёт `Cannot find module '@discordjs/opus'` и не пишет в базу -- поэтому и не убираем `node.cmd`.
- **роли и кнопки очереди (v2.16)** тоже проверены стендом на реальном `index.js`: роль, снятая за секунды до выхода, не возвращается при входе (и по gateway-событию журнала, и по REST-запросу) -- при этом роль, выданная перед выходом, сохраняется, а если возвращать нечего, старая запись стирается; пустой или сбойный список участников не превращается в «все вышли» (никому не выписывается таймаут); кнопки под `/queue` ставят/снимают треки с теми же номерами, что `/remove`, отбивают не-DJ и не дают листать чужую очередь.
- **очередь по 25 треков, стрелки «⬆/⬇», `/rolecheck` и интенты (v2.17)** проверены стендом на реальном `index.js`: страница собирается в пределах лимита сообщения (длинные названия срезаются, номера второй страницы продолжаются); «⬆/⬇» переставляют трек с теми же номерами, что `/move` (включая края: на первом месте «⬆» заблокирована), не-DJ отбивается, играющий трек не перезапускается, предзагрузка переезжает, а очередь в базе не сбивается; мгновенное событие и опрос не обрабатывают один переход дважды; `reportIntents` показывает реальное состояние интентов; `/rolecheck` печатает роли, «вернётся при входе» и наказания -- в том числе для человека не с сервера.
- **страница очереди, хранение «навсегда» и приветствие (v2.18)** проверены стендом на реальном `index.js`: страница `/queue` заполняется до лимита сообщения (на живых названиях — 25 строк вместо 22, длина сообщения остаётся в пределах ~1980 символов), автор у треков одного человека не повторяется, листание по-прежнему идёт по показанным номерам; при `save_roles_days: 0` и `bans_history_days: 0` свип не удаляет ничего (а записи без даты убирает всё равно), история и роли живут годами; `welcome_prefix: false` убирает описание бота из ЛС, оставляя сообщение с правилами; `/welcome` и `panda welcome` печатают один и тот же текст; `/forget` реально удаляет роли и историю и не трогает активное наказание.
- **наказания и лог (v2.15)** проверены стендом на реальном `index.js` с настоящей базой: `/unban` снимает таймаут без бана, снимает настоящий бан (и пишет причину в аудит Discord), при ошибке снятия НЕ чистит запись и ничего не пишет в журнал, на «снимать нечего» отвечает честно, обычного участника отбивает; `/bans` показывает сводку за окно (`выходов 2, таймаутов 1, банов 1, снято 1`) и чистит старые записи; свип ключей 🔑 ставит тег один раз, а второй и третий проход молчат и в REST не ходят.

Один честный нюанс: у трека, который «ждёт продолжения» и был переставлен `/move` в середину очереди, хранится и его место (`seek`), но если бот успеет доиграть до него и упасть уже на нём -- он продолжит с того места, где оборвался, уже как обычный текущий трек.

## Хранилище: почему keyv + SQLite

Базы `*.sqlite` (keyv поверх SQLite) -- сознательный выбор, и менять его **не нужно**:

- зависимости уже стоят и собраны (`sqlite3` -- native, в комплекте с портативным Node), новая библиотека = переустановка зависимостей на всех развёртываниях;
- данные лежат **локально в папке бота**, без сервера и интернета -- бот работает и без сети, никакие внешние сервисы не упадут;
- объёмы тут микроскопические (записи о таймаутах, роли, одна очередь музыки), поэтому «быстрее/мощнее» (Postgres/Redis/Mongo) даст только лишние хлопоты: их надо где-то поднимать и беречь;
- важный момент, который уже учтён: в keyv v5 конструктор со строкой-URI **молча уходит в память**, если адаптер не передан явно (`store: new KeyvSqlite(...)`) -- из-за этого база одно время вообще не писалась на диск. Если когда-нибудь менять хранилище, эту ловушку надо проверять так же: записать → выйти → прочитать заново.

Альтернативы на будущее (ждем, пока появится реальная потребность): `better-sqlite3` напрямую -- быстрее и без слоя keyv, но требует нативных сборок; `node:sqlite` -- встроен в Node 24, но его API ещё меняется. Ни одна из них не даст ничего, что было бы видно в работе бота.

## Git

`config.json`, базы и зависимости уже в `.gitignore`. Начало работы:

```bash
git init
git add .
git commit -m "PANDAMIA bot v2.2.3"
```

**Процесс обновлений:** изменения готовит Codebuff и **сам оформляет коммит**;
владелец смотрит `git log` / `git show` -- и **push делает сам** (`git push`).
Так в репозитории всегда лежит восстановимая история: любой коммит можно
откатить (`git revert`) или достать файл из прошлого (`git checkout <hash> -- путь/к/файлу`).
Токен и базы в git не попадают (см. `.gitignore`).
